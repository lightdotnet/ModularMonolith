# Workflow: Sync Documentation

Triggered only by an explicit request to sync/update documentation. This workflow is the canonical home for the doc-writing rules below; [sync-docs](../skills/sync-docs/SKILL.md) and [generate-docs](../skills/generate-docs/SKILL.md) link here rather than repeating them.

## Steps

1. **Confirm scope.** Which backend module/project/folder or frontend area's docs are being synced, or is it genuinely all of them? Don't assume "all" unless the user says so.
2. **Diff each doc in scope**: delegate to [documentation-writer](../agents/documentation-writer.md) (or use facts already verified earlier in the session) to compare the existing doc against current code and determine what's added/updated/removed.
3. **Present one consolidated summary and get one approval.** Before writing anything, list every file that will change and, per file, a short summary of what will change. Ask for a single approval covering the whole batch — never ask file-by-file.
4. **Apply all approved changes**: once approved, write every file in the batch without asking again per file.
5. **Preserve manual documentation**: any clearly human-authored content (explicit "Notes"/manual sections, or content not previously generated by this workflow) must be kept verbatim.
6. **Remove outdated information**: stale facts that no longer match the code must be removed, not left contradicting reality.
7. **Keep all docs synchronized**: if a change in one doc has implications for another in scope (e.g. a backend overview and its dependency graph, or a backend API doc and the frontend integration notes in root `docs/integration.md`), update both consistently within the confirmed scope — don't let them drift apart. `dependency-graph.md` is the one canonical home for a project-reference/import diagram and its circular-reference/boundary-violation checks; `overview.md`/`architecture.md` link to it with a one/two-sentence summary rather than repeating the diagram. Point at the version-of-record file (`Directory.Packages.props` for the backend, `package.json` for a client app) rather than copying exact package version numbers into prose, since those go stale on every bump.
8. **Use the right module-doc shape.** A single-project backend module gets a flat `src/docs/architecture/modules/<ModuleName>.md`; only use the nested `modules/<ModuleName>/overview.md` form for a split (Domain/Application/Infrastructure/Api) module — see [docs/templates/module-overview.md](../docs/templates/module-overview.md).
9. **Write present-tense facts only — never narrate the sync itself into the doc body.** Don't write "new this sync"/"changed this sync"/"unchanged" markers into file content, and don't chain multiple dated notes into a growing footer — every synced file ends in exactly one `_Last synced: <date>_` line, replacing whatever was there before. A reader opening the doc cold should not be able to tell how many times it's been regenerated; the changelog-style summary of what changed belongs in the chat report to the user (step 10), not in the file. A freshly generated doc follows the same rule — it has no history to narrate.
10. **Report**: a changelog-style summary of what was added, updated, and removed, per doc.

## Output

- A pre-write summary (files + planned per-file changes) with a single approval gate before any file is touched.
- Updated documentation files, scoped to what was confirmed, with manual content preserved, narration-free, and each ending in a single `_Last synced: <date>_` line.
- A summary of the sync (added/updated/removed) for the user to review.
