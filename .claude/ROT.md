# ROT.md — Scheduled Maintenance for `.claude/`

This file defines the recurring review that keeps `.claude/` itself healthy: agents, skills, workflows, templates, commands, and the core docs (root `CLAUDE.md`, `AI_CONTEXT.md`, `WORKFLOWS.md`, plus each project's own `src/CLAUDE.md` / `clients/<app-name>/CLAUDE.md` and root `docs/integration.md` — see [../CLAUDE.md §3](../CLAUDE.md#3-where-things-live) for the current doc-ownership layout). It is a **meta-maintenance** doc — it reviews the `.claude/` configuration, not the application code (see [workflows/sync-documentation.md](workflows/sync-documentation.md) for that).

**ROT** = the three things a review looks for:

- **R — Redundant**: two agents/skills/workflows with overlapping responsibility; the same guidance repeated in multiple files instead of cross-linked; a doc template duplicating what another already covers.
- **O — Outdated**: content that no longer matches reality — a broken cross-reference (renamed/deleted file), a described module/route that no longer exists or was renamed, an architecture decision recorded here that the team actually changed, a tech-stack claim in `CLAUDE.md` §1.1 that's since drifted.
- **T — Trivial**: an agent/skill/workflow that's never invoked, adds no value over Claude reasoning inline, or has shrunk to boilerplate that restates the obvious.

Like everything else under `.claude/`, ROT review is **explicit and pull-based** — run it when the user asks, not automatically as a side effect of other work (see `CLAUDE.md` §2.5). Findings are reported; fixes to core docs/templates require the same confirm-before-edit discipline as [sync-documentation](workflows/sync-documentation.md).

## Schedule

| Cadence | Trigger | Scope |
|---|---|---|
| Monthly (or every ~4–6 weeks of active work) | Manual — user runs it | Full `.claude/` sweep |
| After `scaffold-project` completes | One-time, event-based | Reconcile root `CLAUDE.md`/`src/CLAUDE.md`/`clients/<app-name>/CLAUDE.md`/`docs/integration.md` intended-shape sections against what was actually scaffolded |
| After adding/removing a backend module or a client app under `clients/` | Event-based | `src/CLAUDE.md`/`src/docs/`, `clients/<app-name>/CLAUDE.md`/`clients/<app-name>/docs/`, any agent/skill/template/command that names specific modules/apps/routes |
| After a stack/tooling decision changes (e.g. switch data-fetching library, EF Core provider, router style) | Event-based | root `CLAUDE.md` §1, `src/docs/conventions/`/`clients/<app-name>/docs/conventions/`, `src/docs/architecture/architecture.md`/`clients/<app-name>/docs/architecture/architecture.md`, affected agents |
| After a backend `coding-conventions.md` restructure, an EF Core / DDD tactical-convention change, or a Next.js/React major-version bump | Event-based | `agents/{ddd-modeler,dotnet-developer,nextjs-developer}.md` + `skills/{ddd-modeling,clean-architecture-split}.md` — the repo-specific rules and doc-section pointers they bake in (`Light.Specification`/`Light.Domain`, `Result`-not-exceptions, the `Create<Module>Schema` squash rule, `node_modules/next/dist/docs`, the five `lib/server/backend-api.ts` clients) |
| After a module is split into `<Module>.{Domain,Application,Infrastructure,Api}` | Event-based | `skills/clean-architecture-split.md` + `agents/{dotnet-architect,architecture-reviewer}.md` split-mode guidance — they currently say no module uses the split; that stops being true |
| Before a release/milestone tag | Event-based | Full sweep, with emphasis on Trivial (unused agents/skills accumulate over a project's life) |

Track actual runs in the [Review Log](#review-log) below so the next review knows the baseline.

## How to Run It

Ask Claude: *"Run a ROT review of `.claude/` per ROT.md"* (optionally scoped, e.g. "...just the agents" or "...since the last entry in the Review Log"). Expected behavior:

1. Read the [Review Log](#review-log) to find the last reviewed date/scope — a review is a diff since then, not necessarily a full re-read every time.
2. Walk the checklist below for the scope in play.
3. Report findings as a table: file → R/O/T → what's wrong → suggested action. No file edits during this step.
4. Only apply fixes the user explicitly approves — this is a report-then-confirm workflow, same as [review-repository](workflows/review-repository.md), not an autonomous cleanup.
5. Append a row to the Review Log once findings are reported (or once fixes are applied, if the user asked for that too).

## Checklist

### Core docs (root `CLAUDE.md`, `AI_CONTEXT.md`, `WORKFLOWS.md`, `src/CLAUDE.md`, `clients/admin/CLAUDE.md`, root `docs/integration.md`)

- [ ] Every agent/skill/workflow/command link in root `CLAUDE.md` §4–6 and `WORKFLOWS.md` resolves to a file that still exists.
- [ ] `src/CLAUDE.md` § Stack and `clients/admin/CLAUDE.md` § Stack still match what's actually in `src/`/`clients/admin` (or are still correctly marked "intent, not yet verified" if nothing's scaffolded).
- [ ] `src/docs/architecture/`/`clients/admin/docs/architecture/`/`src/docs/conventions/`/`clients/admin/docs/conventions/` "verified" sections aren't silently stale — either they match current code, or they're honestly still `unknown`.
- [ ] No core doc contradicts another (e.g. root `CLAUDE.md` describing a module/app `src/CLAUDE.md`/`clients/admin/CLAUDE.md` doesn't mention, or vice versa) — including root `docs/integration.md` not contradicting either project's own architecture docs.
- [ ] `commands/context-backend.md`/`context-frontend.md`/`context-full.md` still list the correct files to load (they'll go stale if a core doc is ever renamed/relocated again).
- [ ] `src/docs/known-debt.md` reflects current open backend items only — no resolved items lingering, and no debt duplicated back into `src/docs/architecture/architecture.md`/`src/CLAUDE.md`'s own sections (those should just point to it).
- [ ] Core-doc footers stay a single `_Last synced: <date>_` line — no chained "previously X, previously Y" history creeping back in (git log owns that).

### Agents (`agents/*.md`)

- [ ] Each agent is referenced by at least one skill or workflow, or by `CLAUDE.md` §4 — an orphaned agent is a Trivial candidate.
- [ ] No two agents claim overlapping primary responsibility without a clear "defer to X for Y" boundary (check each agent's "Things to Avoid" section for the handoff).
- [ ] `description` frontmatter still accurately scopes the agent (e.g. still says "backend" if that's still true, references the right sibling agents by current filename).
- [ ] Agent still reflects current architecture decisions (e.g. if the project moved away from one `DbContext` per module, `efcore-specialist.md` needs updating — Outdated).
- [ ] The implementer agents (`dotnet-developer`, `nextjs-developer` — the only ones with `Edit`/`Write`/`Bash`) still state, in both `description` and body, that they run **only after a plan is approved**, do build/lint-sanity but **never the test suite**, and never edit `docs/` as a side effect. A loosening here silently undermines the `CLAUDE.md` §2.9 gate.
- [ ] The design → implement → review pipeline stays clean per stack: design agents (`dotnet-architect`/`ddd-modeler`/`api-designer`, `nextjs-architect`) don't gain write tools, the `*-developer` agents don't drift into design or review scope, and the review agents don't start rewriting. `ddd-modeler` still defers *up* to `dotnet-architect` (module/project structure, bounded contexts) and *sideways* to `architecture-reviewer` (layer direction) / `efcore-specialist` (persistence mapping) — check its `description` + "Things to Avoid".
- [ ] `ddd-modeler` / `dotnet-developer` / `nextjs-developer` bake in live repo specifics (`Light.Specification` / `Light.Domain`, `Result`-not-exceptions, the `Create<Module>Schema` migration-squash rule, `node_modules/next/dist/docs`, the five `lib/server/backend-api.ts` clients, and named sections of the two `coding-conventions.md`) — verify each still matches current code/docs; Outdated if a cited rule, path, or section name has moved.

### Skills (`skills/*.md`)

- [ ] Each skill is referenced from `CLAUDE.md` §5, a workflow, or another skill — otherwise flag as possibly Trivial.
- [ ] Skill's `Workflow` steps still name agents/skills that exist under their current filenames.
- [ ] No two skills cover the same task with diverging advice (Redundant) — if they do, decide which is canonical and fold/cross-link the other.
- [ ] `clean-architecture-split.md` still states that no module uses the 4-project split and single-project is the default. Once a module *is* split, this is Outdated — the skill needs a real worked example and `dotnet-architect`/`architecture-reviewer`'s split-mode guidance stops being hypothetical.

### Workflows (`workflows/*.md`)

- [ ] `WORKFLOWS.md` index table matches the actual files in `workflows/` (no missing rows, no rows for deleted files).
- [ ] Each workflow's steps still reference current agent/skill filenames.
- [ ] A workflow that's never matched a real request in practice (ask the user) is a Trivial candidate for trimming or merging.

### Doc templates (`docs/templates/*.md`)

- [ ] Every template is still used by at least one skill/agent/workflow reference.
- [ ] Template `Output location` comments still match the actual per-project `docs/` layout (`src/docs/{architecture,conventions}/` for backend, `clients/<app-name>/docs/{architecture,conventions}/` per client app).
- [ ] No template duplicates another's structure (Redundant) — e.g. two templates both trying to own "module-level architecture."

### Model currency (agents, skills, workflows, commands)

- [ ] No agent frontmatter pins a `model:` field to a specific model unless there's a deliberate, still-valid reason (e.g. a cost/latency trade-off) — an unpinned agent inherits whatever model the session is actually running on, which is usually what's wanted; a stale pin silently keeps using an old model even after the user's default has moved on. Outdated if a pin references a model no longer available.
- [ ] No agent/skill/workflow body prose hardcodes a specific model name/version (e.g. "Claude 3.5 Sonnet," "GPT-4") or a capability workaround tied to an old model's limitations (a context-window size, a "this model tends to X so avoid Y" instruction) — these go stale every time the underlying model changes and this repo's own `CLAUDE.md`/agents are meant to stay model-agnostic. Outdated if found; note the current model in use at review time for context (see the session's own environment info) but don't hardcode it into the fix either.
- [ ] Check for guidance that made sense for a weaker/older model but is now unnecessary overhead for a current one (e.g. excessive hand-holding, step-by-step spelling-out of something a capable current model would infer) — a Trivial candidate for trimming, not an Outdated one (the instruction isn't wrong, just no longer earning its keep).
