## Architecture decisions pending

- **D1 — `Identity` and `Notifications` CQRS handlers are thin pass-throughs to their service classes.** All `Identity` writes and user search dispatch through mediator commands/queries (`Identity.Api/Application/Users/{Commands,Queries}`, `Identity.Api/Application/Roles/Commands`), and every `Notifications` controller action does the same. In both modules controllers only bind the module's `Contracts` DTO/route param and dispatch a command/query, but every handler just forwards to the service layer — `IUserService`/`IRoleService` in `Identity`, `INotificationService`/`IHubService` in `Notifications` — which still holds the logic; the one exception is `Identity`'s `SearchUserQueryHandler`, which queries `UserManager<User>` directly. (Command handlers that additionally publish an integration event — e.g. `CreateUserCommandHandler` — still delegate the actual work to the service.) Decide: inline the service logic into the handlers and demote the services to internal read-only helpers (the `SearchUserQueryHandler` model), or keep the services as the logic layer and treat the handlers as a deliberate uniform entrypoint. *(User: to be implemented separately.)*
- **D2 — Soft-delete is wired up but disabled.** `IdentityDbContext` calls `AuditEntries(..., enableSoftDelete: false)` even though `User` implements `ISoftDelete` and `AuthenticationService.CheckInvalidUser` checks `user.Deleted != null` (currently dead code — `AuthenticationService` short-circuits on `user is null` first, so this is an audit-trail/anonymization gap, not a login-bypass risk). `UserService.DeleteAsync` hard-deletes immediately after `User.Delete()` anonymizes the row, wasting that work; a hard-deleted user's `Id` also orphans any FK/audit field that referenced it. Decide: flip `enableSoftDelete: true`, or remove `ISoftDelete`/`Deleted`/`DeletedBy` if hard delete is genuinely intended.
- **D4 — `GET user` vs. `GET user/search` coexist.** `UserController` exposes both an unbounded `GET user` (`IEnumerable<UserDto>`) and a paginated `GET user/search` (`PagedResult<UserDto>`, query params via `Identity.Contracts/SearchUserRequest.cs`) for the same read use case. Decide whether `GET user` is an intentional "admin/all" escape hatch or should be deprecated now that paginated search exists.
- **D6 — Standalone `Identity.Web` host has no cross-module notification handlers.** `ExternalLoginService` publishes `ExternalUserProvisionedIntegrationEvent` after JIT-provisioning a Microsoft user; its only handler (`ExternalUserProvisionedIntegrationEventHandler`) lives in `Notifications.Api`, which the standalone host neither references (the `.Contracts`-only boundary rule) nor assembly-scans. So `IPublisher.Publish` silently no-ops there and a JIT-provisioned Microsoft user gets no welcome email under the standalone host — the co-host (`StarterKit.WebApi`, scans all module assemblies) is fine. The same applies to `UserCreatedIntegrationEvent` if a Razor page ever creates a user. Accepted: the standalone host is login-only. Revisit if it ever needs to be a full runtime.
- **D5 — Cross-module display labels are denormalized snapshots with no backfill.** `Approval` cannot resolve identity/organization data, so the calling side supplies `ApprovalRequest.RequesterName` / `ApprovalStep.ApproverName` at creation time and the module stores them verbatim (same rationale as `Notifications`' caller-supplied `fromName`). `LeaveManagement` has the same exposure a second time: it resolves `RequesterName` server-side via `Organization`'s `IOrgDirectoryService.GetEmployeeNameAsync` rather than trusting the client, but the resulting label is still written once into `ApprovalRequest.RequesterName`/`ApprovalStep.ApproverName` and never re-synced. Either way, these go stale if the underlying user/employee is later renamed, and there is no re-sync path. Accepted as the cost of the "Approval never reaches into other modules" boundary; revisit only if stale approver/requester labels become a real complaint.

## Correctness / performance

- **P4 — `IServiceClaimService` has no registered implementation** (commented out in `Identity.Api/DependencyInjection.cs`; interface in `Identity.Contracts/Services/IServiceClaimService.cs`). Either implement and register it, or remove the unused contract. *(User: later.)*
- **P5 — `IdentityClaimQueryExtensions.CheckUserHasClaimAsync` is dead code** (`Identity.Api/Services/IdentityClaimQueryExtensions.cs`, never called). Wire it into a permission check or remove it. *(User: later.)*
- **P6 — Domain-event dispatch convention bypassed in `Identity`.** `DispatchDomainEventsExtensions.DispatchDomainEvents` (`src/Persistence/Extensions/`) is never called from `IdentityDbContext.SaveChanges[Async]`. Identity has no `BaseEntity` domain events at all — instead it has **two** manual `IPublisher.Publish` sites for `Contracts`-level integration events: `UserCreatedIntegrationEvent` from `CreateUserCommandHandler`, and `ExternalUserProvisionedIntegrationEvent` from `ExternalLoginService`. Unifying these onto the `DispatchDomainEvents` convention is blocked on D1 (the CQRS-handler / service split) and on `User` becoming event-capable (it is a raw `IdentityUser`, not a `BaseEntity`). This is now an `Identity`-only gap: `ApprovalDbContext.SaveChangesAsync` calls `publisher.DispatchDomainEvents(this)` after the commit (wrapped in try/catch-log) and is the conforming reference for the convention.
- **P7 — `CreateEmployeeLoginCommandHandler`'s cross-module create is still not fully atomic.** The concurrent-double-submit hole is closed (the link is claimed with a conditional `ExecuteUpdateAsync` on `UserId IS NULL`, and the freshly minted Identity user is deleted via `IUserService.DeleteAsync` when that loses the race or when `SetClaimAsync` throws). Residual gaps: (1) the conditional `ExecuteUpdateAsync` bypasses the audit interceptor, so linking does not stamp `Employee.LastModified`/`LastModifiedBy`; (2) the compensation is itself best-effort — if it throws, an orphan Identity user can still remain. A durable fix needs an outbox/saga or a real distributed transaction.
- **P8 — `LeaveManagement` ↔ `Approval` create/resubmit consistency is ordering + best-effort compensation, not a shared transaction.** `CreateLeaveRequestCommandHandler` creates the `Approval` workflow first and does a single local commit afterwards (on approval-create failure nothing is persisted locally; on local-save failure a best-effort `IApprovalService.CancelAsync` compensates). The `UpdateLeaveRequestCommandHandler` resubmit path is cancel-old → create-new → then apply the local edit + local commit; that final commit is now also wrapped in a best-effort `CancelAsync(newApprovalId)` compensation mirroring the create handler. Same shape as P7: no cross-`DbContext` transaction — the five module contexts alias one physical DB, but `TransactionScope` across them promotes to MSDTC, unavailable on the container targets. Residual accepted windows: (1) on resubmit, if the cancel of the old workflow succeeds but the new `CreateAsync` fails, the local row stays `Pending` pointing at a now-cancelled workflow; (2) on resubmit, if both the cancel-old and create-new succeed but the local `SaveChangesAsync` throws, the compensation attempts to cancel the new workflow, but if that compensation also throws the row stays `Pending` pointing at the new workflow with the old fields. Either way the next `LeaveRequestReconciliationService` tick (default 5 min) reconciles the local status. Status drift itself is event-driven (an `ApprovalFinalizedIntegrationEvent` subscriber) with that periodic backstop, not repaired on read.
- **`LeaveManagement` status-reconcile writes are mis-attributed in the audit trail.** When `LeaveRequest.Status` is reconciled by the `ApprovalFinalizedIntegrationEventHandler` (runs in the deciding approver's HTTP scope) the audit interceptor stamps `LastModifiedBy` with the *approver's* user id, not the requester's and not a system principal; when the `LeaveRequestReconciliationService` sweep does the same write it runs with no `HttpContext`, so `LastModifiedBy` is stamped `null`. There is no general-purpose registered "system principal" `ICurrentUser` to attribute these background/cross-user writes to (`MigratorCurrentUser` is `internal` to `Persistence.MigrationSupport` and migration-specific). Accepted for now — revisit if the leave-request audit trail is ever surfaced to users.
- **`Notifications`: no index on `Status`.** `NotificationDbContext`'s only index is `HasIndex(x => x.ToUserId)`, but both list queries and `CountUnreadAsync` filter on `Status` (often combined with `ToUserId`). Performance follow-up candidate at scale, not proven today.
- **`Approval`'s by-source-record status lookups return the most recent of N matches, silently.** `(RequestType, RequestId)` is a non-unique opaque reference, so `GetStatusByRequestAsync` orders by `Created` desc and takes the first `ApprovalStatusView`; `GetStatusesByRequestAsync` keeps the first row per `RequestId` group over the same newest-first ordering. Multiple approval requests per source record now occur in normal operation — `LeaveManagement`'s resubmit path cancels the old workflow and creates a fresh one for the same `LeaveRequest.Id` — and the newest-first ordering is what makes the lookups resolve to the active workflow. A caller that assumed a strict 1:1 mapping would still not be warned when more than one row exists.
- **`NotificationConstants.ServerNotification` is effectively dead.** It is referenced only by `HubService.NotifyAsync` (the broadcast overloads), which itself has **zero callers** anywhere in the module or host. The wired push path (`HubService.SendAsync<T>`) uses `typeof(T).Name` as the SignalR event name instead. Remove `NotifyAsync` + the constant, or wire a real broadcast use case.
- **Migration-time domain-event dispatch may silently miss module handlers.** `MigrationsExtensions.AddMigrationsServices` (`src/Persistence/MigrationSupport/`) registers mediator handlers via `Assembly.GetExecutingAssembly()`, which resolves to the `Persistence` assembly, not the module assemblies. Revisit once a module actually relies on migration-time dispatch.

## Security / authorization

- **Hub-token audience isolation leans on the current Wilson/JwtBearer `ValidateAudience` semantics.** The fail-closed control keeping the SignalR hub token off `/api` is the dedicated `"HubBearer"` sub-scheme (validates `aud == Jwt:HubAudience`); `HubTokenApiGuardHandler` is a fail-open backstop for bare `[Authorize]` endpoints. The `"Bearer"` scheme additionally sets a custom `AudienceValidator` that accepts an audience-less token and rejects one carrying the hub audience — this relies on `Microsoft.IdentityModel`'s current `ValidateAudience` short-circuit behaviour for tokens with no `aud` claim. Re-verify on any `Microsoft.IdentityModel` / `JwtBearer` major upgrade.
- **No self-service "link my existing local account to Microsoft" flow.** `ExternalLoginService` rejects (`EmailAlreadyRegistered`) an external identity whose email matches an already-registered local user rather than linking it — deliberate (the nOAuth attack class), but it means a user with a pre-existing local account can only get Microsoft sign-in via an administrator action, and no such admin action exists yet either.
- **`AuthProviderWire` is an interim.** `UserDto` / `CreateUserRequest` still expose `AuthProvider` as `string?` over the API (`null` / `"AD"` / `"Microsoft"`), bridged to the `AuthProvider` enum by `AuthProviderWire`. Aligning the wire contract to the enum — or dropping the field from the create contract entirely — is an open api-designer question.
- **`GET employee/search` is readable by any authenticated user, by design — the PII boundary now lives in one `.Select`.** The class-level `[MustHavePermission(Employees.View)]` gate was removed from `EmployeeController.SearchAsync` so the create-approval-request approver picker (and any future company-directory feature) can look employees up; `GET employee/{id}` and every write stay permission-gated. `SearchEmployeesQueryHandler` projects only basic directory fields via an explicit `.Select` — any sensitive column added to `Employee` later is exposed company-wide the moment it is added to that projection. Keep the search projection slim.
- **`LeaveManagementPermissions` has no `View`/`ViewAll` split — `Requests.Manage` alone grants view-all.** Every other module's admin-facing permission catalog separates "view" from "create/update/delete". `LeaveManagement` instead has a single `leave.requests.manage` permission that grants both view-all and delete-any. Not a vulnerability today, but a future read-only manage-adjacent role has no permission to slot into.

## Structural / code quality

- **`Identity` predates the module structure convention** (adopted 2026-07-30) and doesn't fully conform: internal layering is informal (folder-based, not compiler-enforced) and CQRS handlers still delegate to the traditional service classes (see D1). `Identity.Web` (added later) is a clean Razor Pages host inside the same module. Treat as pending `Identity` cleanup, not a second convention. `Notifications`/`Organization`/`Approval`/`LeaveManagement` do conform.
- **`Identity.Web` and `StarterKit.WebApi` still hand-compose the Identity platform + mediator independently.** The behaviour gap is closed — `IdentityWebHost.AddIdentityWebHost` now registers the same `LoggingBehaviour`/`ValidationBehaviour` and `AddValidatorsFromAssemblies` as the co-host. The remaining drift is scan scope: the standalone host scans the Identity assembly alone (1) vs. the co-host's 6, so it has no cross-module handlers (see D6), and the two compositions are still maintained separately with no shared helper. Candidate fix: a shared `AddIdentityHost(IServiceCollection, IConfiguration)` both hosts call.
- **`ApiControllerBase`/`VersionedApiController` duplicate a `_mediator` backing-field + lazy `Mediator` property** (`src/Infrastructure/Endpoints/`). Likely unavoidable since they derive from two different vendor base classes.
- **`UserSession` extends the plain vendor `Entity` base type, not `AuditableEntity`** — no decision made on whether it should carry an audit trail.
- **`Entities/UserToken.cs`** (ASP.NET Core Identity's built-in `IdentityUserToken<string>`, external-login-provider token store) sits in the same `Entities/` folder as `UserSession` (this module's JWT/session entity) — "token" means two unrelated things in this module. Low-cost mitigation: a one-line comment, or grouping ASP.NET Identity's built-in entities separately.

## Test coverage

- **No `tests/Notifications.Tests` project** — `Identity` has 123 tests, `Organization` 63, `Approval` 68, `LeaveManagement` 122; `Notifications` still has no automated coverage. The host-owned auth composition also has no dedicated tests yet (`ExternalLoginService` itself is now covered by `tests/Identity.Tests/Services/ExternalLoginServiceTests.cs`).
- **No provider-specific migration smoke test.** The `CreateIdentitySchema` (MSSQL baseline, regenerated 2026-09-08) / `CreateApprovalSchema` (MSSQL baseline, regenerated 2026-09-09 as `20260909114331` — adds the `ConcurrencyToken` column, widens the `(RequestType, RequestId)` index to include `Created`, and replaces the non-unique `ApprovalSteps.ApprovalRequestId` index with a unique `(ApprovalRequestId, Level)` index) / `CreateOrganizationSchema` / `CreateLeaveManagementSchema` baselines are exercised only through the Sqlite in-memory test hosts and `dotnet ef migrations script`. A real MSSQL/PostgreSQL run has not been done in CI. The PostgreSQL and Sqlite `Approval` baselines are deliberately left un-regenerated (they predate the aggregate/concurrency-token refactor) per the dev migration squash convention.

## Dependency hygiene

- **Likely dead package references** (no source usage found): `Lightsoft.EventBus` (`Shared.csproj`), `Lightsoft.FileGenerator` (`Infrastructure.csproj`). Also a centrally-pinned `Microsoft.AspNetCore.Authentication.MicrosoftAccount` version with no project referencing it (the OIDC scheme uses `AddOpenIdConnect`, not `AddMicrosoftAccount`). Verify and remove if confirmed unused.
- **Undeclared transitive dependencies** — compile only because a `ProjectReference` happens to bring the package along:
  - `Infrastructure` uses `Mapster` and `Lightsoft.AspNetCore.Authorization`/`Lightsoft.Result` without declaring either (rides on `Shared`).
  - `Identity.Api` uses `Lightsoft.AspNetCore.Authorization`, `Lightsoft.Result`, `Lightsoft.Extensions`, `Lightsoft.Mediator` (via `GlobalUsings.cs`) without declaring any of them. (`Identity.Contracts` now declares `Lightsoft.Mediator`/`Lightsoft.Result` directly — only its use of `Lightsoft.AspNetCore.Authorization` is still transitive.)
  - `Identity.Api`'s `SearchUserQueryHandler` uses `Light.Specification` (`WhereIf`), provided by `Lightsoft.EntityFrameworkCore` declared by `Persistence.csproj`.
  - `StarterKit.WebApi` uses `Lightsoft.Serilog` without declaring it (only `Infrastructure.csproj` does).
  - Fragile: if an upstream project drops one of these packages, downstream projects break with no direct signal why. Recommend each project explicitly declare what it directly uses. `Organization`/`Approval`/`LeaveManagement` don't have this problem.
