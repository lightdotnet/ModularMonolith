## Architecture decisions pending

- **D1 — `Identity` and `Notifications` CQRS handlers are thin pass-throughs to their service classes.** All `Identity` writes and user search dispatch through mediator commands/queries (`Identity.Api/Application/Users/{Commands,Queries}`, `Identity.Api/Application/Roles/Commands`), and every `Notifications` controller action does the same. In both modules controllers only bind the module's `Contracts` DTO/route param and dispatch a command/query, but every handler just forwards to the service layer — `IUserService`/`IRoleService` in `Identity`, `INotificationService`/`IHubService` in `Notifications` — which still holds the logic; the one exception is `Identity`'s `SearchUserQueryHandler`, which queries `UserManager<User>` directly. (Command handlers that additionally publish an integration event — e.g. `CreateUserCommandHandler` — still delegate the actual work to the service.) Decide: inline the service logic into the handlers and demote the services to internal read-only helpers (the `SearchUserQueryHandler` model), or keep the services as the logic layer and treat the handlers as a deliberate uniform entrypoint. *(User: to be implemented separately.)*
- **D2 — Soft-delete is wired up but disabled.** `IdentityDbContext` calls `AuditEntries(..., enableSoftDelete: false)` even though `User` implements `ISoftDelete` and `AuthenticationService.CheckInvalidUser` checks `user.Deleted != null` (currently dead code — `AuthenticationService` short-circuits on `user is null` first, so this is an audit-trail/anonymization gap, not a login-bypass risk). `UserService.DeleteAsync` hard-deletes immediately after `User.Delete()` anonymizes the row, wasting that work; a hard-deleted user's `Id` also orphans any FK/audit field that referenced it. Decide: flip `enableSoftDelete: true`, or remove `ISoftDelete`/`Deleted`/`DeletedBy` if hard delete is genuinely intended.
- **D4 — `GET user` vs. `GET user/search` coexist.** `UserController` exposes both an unbounded `GET user` (`IEnumerable<UserDto>`) and a paginated `GET user/search` (`PagedResult<UserDto>`, query params via `Identity.Contracts/SearchUserRequest.cs`) for the same read use case. Decide whether `GET user` is an intentional "admin/all" escape hatch or should be deprecated now that paginated search exists.
- **D6 — Standalone `Identity.Web` host has no cross-module notification handlers.** `ExternalLoginService` publishes `ExternalUserProvisionedIntegrationEvent` after JIT-provisioning a Microsoft user; its only handler (`ExternalUserProvisionedIntegrationEventHandler`) lives in `Notifications.Api`, which the standalone host neither references (the `.Contracts`-only boundary rule) nor assembly-scans. So `IPublisher.Publish` silently no-ops there and a JIT-provisioned Microsoft user gets no welcome email under the standalone host — the co-host (`StarterKit.WebApi`, scans all module assemblies) is fine. The same applies to `UserCreatedIntegrationEvent` if a Razor page ever creates a user. Accepted: the standalone host is login-only. Revisit if it ever needs to be a full runtime.
- **D5 — Cross-module display labels are denormalized snapshots with no backfill.** `Approval` cannot resolve identity/organization data, so the calling side supplies `ApprovalRequest.RequesterName` / `ApprovalStep.ApproverName` at creation time and the module stores them verbatim (same rationale as `Notifications`' caller-supplied `fromName`). `LeaveManagement` and `Purchasing` have the same exposure: each resolves `RequesterName` server-side via `Organization`'s `IOrgDirectoryService.GetEmployeeNameAsync` rather than trusting the client, but the resulting label is still written once into `ApprovalRequest.RequesterName`/`ApprovalStep.ApproverName` and never re-synced. Either way, these go stale if the underlying user/employee is later renamed, and there is no re-sync path. Accepted as the cost of the "Approval never reaches into other modules" boundary; revisit only if stale approver/requester labels become a real complaint.
- **D7 — The base currency cannot be changed in v1.** `Currency.CreateBase` is the only way a currency becomes the base, called only by the seeder, and no operation flips `IsBase`; there is no endpoint to reassign it. Recorded rates and every order amount are relative to whichever currency was seeded as base, so changing it later would require re-basing all of that history. Accepted for v1; revisit if a template deployment ever needs a non-`VND` base or a base change after go-live.
- **D8 — `Purchasing` hard-codes the shared-kernel default currency for purchase costs instead of reading the base currency from `Currency`.** `PurchaseOrder`/`PurchaseOrderLine.UnitCost` and the add/update-line handlers construct `Money` with `CurrencyConstants.Default` directly; `Purchasing.Api` has no dependency on `Currency.Contracts`. This only produces correct amounts (matching Inventory's base-currency valuation) while the seeded base currency is `CurrencyConstants.Default` — a deployment that changes the base (were D7 ever resolved) would silently misprice purchase costs. Decide: give `Purchasing` a dependency on `Currency.Contracts`/`ICurrencyService` like `Orders`/`Catalog`, or explicitly accept the coupling to the shared-kernel constant.
- **D9 — A `Location` of type `Bin` can only be parented under a `Warehouse`, never a `Store`.** `LocationContextInitialiser` seeds the `BIN` location type with `AllowedParentTypeId = "WAREHOUSE"` and `LocationType`'s aggregate invariant enforces it from there — a small-format store that wants in-store bin locations has no type to model them with today. Accepted for v1; revisit if in-store bin locations are actually needed, either by relaxing `BIN`'s allowed parent or seeding a store-scoped equivalent type.

## Correctness / performance

- **P4 — `IServiceClaimService` has no registered implementation** (commented out in `Identity.Api/DependencyInjection.cs`; interface in `Identity.Contracts/Services/IServiceClaimService.cs`). Either implement and register it, or remove the unused contract. *(User: later.)*
- **P5 — `IdentityClaimQueryExtensions.CheckUserHasClaimAsync` is dead code** (`Identity.Api/Services/IdentityClaimQueryExtensions.cs`, never called). Wire it into a permission check or remove it. *(User: later.)*
- **P6 — Domain-event dispatch convention bypassed in `Identity`.** `DispatchDomainEventsExtensions.DispatchDomainEvents` (`src/Persistence/Extensions/`) is never called from `IdentityDbContext.SaveChanges[Async]`. Identity has no `BaseEntity` domain events at all — instead it has **two** manual `IPublisher.Publish` sites for `Contracts`-level integration events: `UserCreatedIntegrationEvent` from `CreateUserCommandHandler`, and `ExternalUserProvisionedIntegrationEvent` from `ExternalLoginService`. Unifying these onto the `DispatchDomainEvents` convention is blocked on D1 (the CQRS-handler / service split) and on `User` becoming event-capable (it is a raw `IdentityUser`, not a `BaseEntity`). This is now an `Identity`-only gap: `ApprovalDbContext.SaveChangesAsync` calls `publisher.DispatchDomainEvents(this)` after the commit (wrapped in try/catch-log) and is the conforming reference for the convention.
- **P7 — `CreateEmployeeLoginCommandHandler`'s cross-module create is still not fully atomic.** The concurrent-double-submit hole is closed (the link is claimed with a conditional `ExecuteUpdateAsync` on `UserId IS NULL`, and the freshly minted Identity user is deleted via `IUserService.DeleteAsync` when that loses the race or when `SetClaimAsync` throws). Residual gaps: (1) the conditional `ExecuteUpdateAsync` bypasses the audit interceptor, so linking does not stamp `Employee.LastModified`/`LastModifiedBy`; (2) the compensation is itself best-effort — if it throws, an orphan Identity user can still remain. A durable fix needs an outbox/saga or a real distributed transaction.
- **P8 — `LeaveManagement`/`Purchasing` ↔ `Approval` create/resubmit consistency is ordering + best-effort compensation, not a shared transaction.** `CreateLeaveRequestCommandHandler` creates the `Approval` workflow first and does a single local commit afterwards (on approval-create failure nothing is persisted locally; on local-save failure a best-effort `IApprovalService.CancelAsync` compensates). The `UpdateLeaveRequestCommandHandler` resubmit path is cancel-old → create-new → then apply the local edit + local commit; that final commit is also wrapped in a best-effort `CancelAsync(newApprovalId)` compensation mirroring the create handler. `Purchasing`'s `SubmitPurchaseOrderCommandHandler` follows the create shape (workflow first, one local commit, best-effort cancel on save failure). Same shape as P7: no cross-`DbContext` transaction — the module contexts alias one physical DB, but `TransactionScope` across them promotes to MSDTC, unavailable on the container targets. Residual accepted windows (leave resubmit): (1) if the cancel of the old workflow succeeds but the new `CreateAsync` fails, the local row stays `Pending` pointing at a now-cancelled workflow; (2) if both the cancel-old and create-new succeed but the local `SaveChangesAsync` throws, the compensation attempts to cancel the new workflow, but if that compensation also throws the row stays `Pending` pointing at the new workflow with the old fields. Either way the next reconciliation sweep tick reconciles the local status. Status drift itself is event-driven (an `ApprovalFinalizedIntegrationEvent` subscriber) with that periodic backstop, not repaired on read.
- **`PendingApproval` reconciliation sweeps can starve on old pending rows.** Both `LeaveRequestReconciliationService` and `Purchasing`'s `PurchaseOrderApprovalReconciliationService` take the oldest pending rows first (`OrderBy(Created).Take(batchSize)`); a backlog larger than the batch that `Approval` keeps reporting as still pending starves newer rows of the backstop. The integration event is the primary path, so this only bites when a delivery was missed.
- **Background and cross-user writes are mis-attributed in the audit trail.** There is no general-purpose registered "system principal" `ICurrentUser` (`MigratorCurrentUser` is `internal` to `Persistence.MigrationSupport` and migration-specific). Consequences: (1) `LeaveManagement` status reconciles by `ApprovalFinalizedIntegrationEventHandler` (runs in the deciding approver's HTTP scope) stamp `LastModifiedBy` with the *approver's* user id, not the requester's; (2) every `BackgroundService` write (`LeaveRequestReconciliationService`, `Orders`' `OrphanedStockReconciliationService` fence, the `Transfers`/`Purchasing` posting and approval sweeps) runs with no `HttpContext`, so `LastModifiedBy` is stamped `null` (the `Inventory` ledger rows those sweeps cause do carry a `system:*` `PerformedByUserId`). Accepted for now — revisit if these audit trails are ever surfaced to users.
- **`Orders` ↔ `Inventory` stock placement is two commits, not a shared transaction; `OrphanedStockReconciliationService` is the backstop with residual risks.** `PlaceOrderCommandHandler` posts the decrement (Inventory's own commit) before its own `SaveChangesAsync`; a crash or save failure in between leaves stock decremented against a never-placed order. A retry self-heals (the decrement is idempotent via `order-place:{orderId}:{lineId}`), `PlaceOrder` compensates a failed save, `CancelOrder` always attempts a restore, and the sweep restores stock for old never-placed `Draft`/`Cancelled` orders that still hold an unreversed decrement (fenced through `Order.MarkStockReconciled`, restore bounded by a `postedBefore` cutoff). Residual risks: (1) a narrow window between the fence commit and the restore in which a `PlaceOrder` that loads the fenced order can still see the orphan's placement key, skip its decrement, and commit while the sweep then restores that stock; (2) the placement key is per order line, not per quantity, so re-placing an orphan `Draft` whose line quantity was edited after the failed placement finds the old key, skips the decrement, and leaves the stale quantity decremented; (3) each pass scans every never-placed `Draft`/`Cancelled` order older than the cutoff (abandoned carts included) and queries Inventory for each page, so the pass grows with the number of abandoned drafts (the watermark and per-tick page cap only bound one tick).
- **`Inventory` valuation gaps.** (1) Stock that existed before valuation was introduced is valued at 0 until revalued (the column default), so valuation totals and outbound cost are understated until then. (2) `IInventoryService` does not support mixing inbound and outbound movements for the same product/location in one call (only the net delta is availability-checked).
- **`Transfers`/`Purchasing` ↔ `Inventory` postings are two commits per document (`Posting` first, then the outcome); crash windows are recovered only by sweeps.** `TransfersPostingReconciliationService` and `PurchasingPostingReconciliationService` roll stuck `Posting` documents forward (or void/abort on a deterministic refusal with nothing landed). A document that fails transiently on every tick stays `Posting` indefinitely (`Purchasing` logs one that has been stuck for many grace periods at Error; `Transfers` does not distinguish it). Nothing posted to Inventory is ever reversed by design.
- **`Notifications`: no index on `Status`.** `NotificationDbContext`'s only index is `HasIndex(x => x.ToUserId)`, but both list queries and `CountUnreadAsync` filter on `Status` (often combined with `ToUserId`). Performance follow-up candidate at scale, not proven today.
- **`Approval`'s by-source-record status lookups return the most recent of N matches, silently.** `GetStatusByRequestAsync`/`GetStatusesByRequestAsync` treat `(RequestType, RequestId)` as a non-unique opaque reference, ordering by `Created` desc and taking the newest `ApprovalStatusView` per id. No module calls these today — `LeaveManagement` and `Purchasing` both reconcile by the stored approval request id instead (`GetStatusAsync`/`GetStatusesAsync`) — but a future caller of the by-source-record lookups would not be warned when more than one row exists for the same source record (multiple approval requests per source record occur in normal operation: both modules' resubmit paths create a fresh workflow for the same source id).
- **`NotificationConstants.ServerNotification` is effectively dead.** It is referenced only by `HubService.NotifyAsync` (the broadcast overloads), which itself has **zero callers** anywhere in the module or host. The wired push path (`HubService.SendAsync<T>`) uses `typeof(T).Name` as the SignalR event name instead. Remove `NotifyAsync` + the constant, or wire a real broadcast use case.
- **Migration-time domain-event dispatch may silently miss module handlers.** `MigrationsExtensions.AddMigrationsServices` (`src/Persistence/MigrationSupport/`) registers mediator handlers via `Assembly.GetExecutingAssembly()`, which resolves to the `Persistence` assembly, not the module assemblies. Revisit once a module actually relies on migration-time dispatch.
- **`Persistence/Repositories/DynamicTableRepository<T,TEntity,TContext>` has no optimistic-concurrency token.** `Update` reads the current rows for a given `objectName`, mutates the tracked instances in place, and saves — two concurrent `Update` calls for the same `objectName` are last-writer-wins with no conflict detection. Documented in the class XML doc, not fixed. Zero consumers today; before relying on this under concurrent writes, configure a concurrency token (e.g. `IsConcurrencyToken()` on a `LastModified` column) on the entity in the consuming `DbContext`'s model configuration.
- **`ICurrencyService.GetBaseCurrencyAsync` is not cached.** Every call (`CurrencyService`) runs a fresh `Currencies` query for the single base-currency row; `CreateOrderCommandHandler` and `AddOrderLineCommandHandler` each call it at least once per request. Fine at current scale — the row is tiny and indexed via the filtered unique `IsBase` index — but a candidate for a short-lived cache if it becomes a hot path.
- **No exchange-rate feed.** Rates are entered manually through `POST exchange_rate`; there is no scheduled import from an external rate source. A currency with no rate recorded yet — or none covering "now" — makes any order line in that currency fail with `ExchangeRateNotFoundException` until an operator records one.
- **Multi-currency rounding is inconsistent by design.** `Order.Subtotal`/`DiscountAmount`/`Total` and `AmountPaid` are computed/stored as unrounded decimals — only a converted line's unit price is rounded (once, via `CurrencyRounding.RoundToMinorUnits`) at the point of conversion. A base currency with more than 2 decimal places is rejected outright when a line is added, since `Orders`' `Money` columns are `decimal(18,2)`. Both are accepted limitations of the v1 base-currency-only design, not bugs.

## Security / authorization

- **Hub-token audience isolation leans on the current Wilson/JwtBearer `ValidateAudience` semantics.** The fail-closed control keeping the SignalR hub token off `/api` is the dedicated `"HubBearer"` sub-scheme (validates `aud == Jwt:HubAudience`); `HubTokenApiGuardHandler` is a fail-open backstop for bare `[Authorize]` endpoints. The `"Bearer"` scheme additionally sets a custom `AudienceValidator` that accepts an audience-less token and rejects one carrying the hub audience — this relies on `Microsoft.IdentityModel`'s current `ValidateAudience` short-circuit behaviour for tokens with no `aud` claim. Re-verify on any `Microsoft.IdentityModel` / `JwtBearer` major upgrade.
- **No self-service "link my existing local account to Microsoft" flow.** `ExternalLoginService` rejects (`EmailAlreadyRegistered`) an external identity whose email matches an already-registered local user rather than linking it — deliberate (the nOAuth attack class), but it means a user with a pre-existing local account can only get Microsoft sign-in via an administrator action, and no such admin action exists yet either.
- **`AuthProviderWire` is an interim.** `UserDto` / `CreateUserRequest` still expose `AuthProvider` as `string?` over the API (`null` / `"AD"` / `"Microsoft"`), bridged to the `AuthProvider` enum by `AuthProviderWire`. Aligning the wire contract to the enum — or dropping the field from the create contract entirely — is an open api-designer question.
- **`GET employee/search` is readable by any authenticated user, by design — the PII boundary now lives in one `.Select`.** The class-level `[MustHavePermission(Employees.View)]` gate was removed from `EmployeeController.SearchAsync` so the create-approval-request approver picker (and any future company-directory feature) can look employees up; `GET employee/{id}` and every write stay permission-gated. `SearchEmployeesQueryHandler` projects only basic directory fields via an explicit `.Select` — any sensitive column added to `Employee` later is exposed company-wide the moment it is added to that projection. Keep the search projection slim.
- **`LeaveManagementPermissions` has no `View`/`ViewAll` split — `Requests.Manage` alone grants view-all.** Every other module's admin-facing permission catalog separates "view" from "create/update/delete". `LeaveManagement` instead has a single `leave.requests.manage` permission that grants both view-all and delete-any. Not a vulnerability today, but a future read-only manage-adjacent role has no permission to slot into.
- **`Approval`'s self-service create endpoint accepts any non-reserved `RequestType`/`RequestId` from any authenticated user.** `UserApprovalController.PostAsync` forces only the requester identity; `RequestType`/`RequestId` are otherwise passed through unvalidated (no allow-list beyond the reserved-type check, no ownership check against a module that isn't reserved). This is now bounded to non-reserved types: `LeaveRequest`/`PurchaseOrder` are rejected by `CreateApprovalRequestCommandValidator`, and `LeaveManagement`/`Purchasing` reconcile by the stored approval request id rather than by `(RequestType, RequestId)`, so a forged request naming a real `LeaveRequest`/`PurchaseOrder` id can no longer shadow the genuine workflow. A document-type catalog `Code` equal to a reserved type's name is not itself blocked — unverified whether that has any practical effect, since document types and request types are unrelated catalogs.

## Structural / code quality

- **`Identity` predates the module structure convention** (adopted 2026-07-30) and doesn't fully conform: internal layering is informal (folder-based, not compiler-enforced) and CQRS handlers still delegate to the traditional service classes (see D1). `Identity.Web` (added later) is a clean Razor Pages host inside the same module. Treat as pending `Identity` cleanup, not a second convention. `Notifications`/`Organization`/`Approval`/`LeaveManagement`/`Location`/`Catalog`/`Currency`/`Orders`/`Inventory`/`Transfers`/`Purchasing` do conform.
- **`Identity.Web` and `StarterKit.WebApi` still hand-compose the Identity platform + mediator independently.** The behaviour gap is closed — `IdentityWebHost.AddIdentityWebHost` now registers the same `LoggingBehaviour`/`ValidationBehaviour` and `AddValidatorsFromAssemblies` as the co-host. The remaining drift is scan scope: the standalone host scans the Identity assembly alone (1) vs. the co-host's assemblies, so it has no cross-module handlers (see D6), and the two compositions are still maintained separately with no shared helper. Candidate fix: a shared `AddIdentityHost(IServiceCollection, IConfiguration)` both hosts call.
- **`ApiControllerBase`/`VersionedApiController` duplicate a `_mediator` backing-field + lazy `Mediator` property** (`src/Infrastructure/Endpoints/`). Likely unavoidable since they derive from two different vendor base classes.
- **`UserSession` extends the plain vendor `Entity` base type, not `AuditableEntity`** — no decision made on whether it should carry an audit trail.
- **`Entities/UserToken.cs`** (ASP.NET Core Identity's built-in `IdentityUserToken<string>`, external-login-provider token store) sits in the same `Entities/` folder as `UserSession` (this module's JWT/session entity) — "token" means two unrelated things in this module. Low-cost mitigation: a one-line comment, or grouping ASP.NET Identity's built-in entities separately.
- **`Persistence/Repositories/ICacheRepository<T>`'s write-path exclusivity is documented, not enforced.** Any entity type adopted through this opt-in whole-table cache-repository must be written exclusively through it — a caller that calls `SaveChanges[Async]` directly on the underlying `DbContext` for that entity type silently leaves the cache stale, with no error raised anywhere. Flagged in the class XML docs (`CacheRepositoryBase<T>`/`ICacheRepository<T>`), not solved. Zero adopters today — `Location`'s `LocationTypeCache` deliberately avoids this repository, sidestepping the hazard by construction instead (see [architecture/modules/Location.md § Notable Conventions](architecture/modules/Location.md#notable-conventions)) — so nothing is broken by this yet; revisit if/when a real consumer adopts `ICacheRepository<T>`.
- **The shared `Money` value object has no cross-currency guard or arithmetic.** It accepts any well-formed ISO-4217-shaped code and is otherwise rule-light — no `+`/`-`, no equality-of-currency check before combining two amounts. Every consumer (`Orders`, `Catalog`, `Purchasing`) must check currency equality itself before summing/comparing two `Money` values; nothing in the type itself would catch a mistake. Accepted as a deliberate "stays rule-light" design (see `Shared/ValueObjects/Money.cs`'s class doc) — revisit only if a real cross-currency arithmetic bug surfaces.

## Test coverage

- **No `tests/Notifications.Tests` project** — every other module has a test project; `Notifications` still has no automated coverage. The host-owned auth composition also has no dedicated tests yet (`ExternalLoginService` itself is covered by `tests/Identity.Tests/Services/ExternalLoginServiceTests.cs`).
- **No provider-specific migration smoke test against a real MSSQL or PostgreSQL server.** Every module's migration set (see [conventions/migrations.md](conventions/migrations.md) for the current baselines per provider) is exercised only through the Sqlite in-memory test hosts and, for MSSQL/PostgreSQL specifically, `dotnet ef migrations script` (generated and read, never applied to a real server). The Sqlite baselines for `Location`/`Catalog`/`Orders`/`Inventory`/`Transfers`/`Purchasing`/`Currency` were applied to a fresh file as part of regenerating them, which is a weaker check than a full up/down cycle against a real server. `Approval`'s PostgreSQL/Sqlite baselines are additionally older than its MSSQL one (they predate the aggregate/concurrency-token refactor: no `ConcurrencyToken` column, still the non-unique `ApprovalSteps.ApprovalRequestId` index) and are left as-is per the dev migration squash convention; `Identity`'s PostgreSQL/Sqlite baselines are likewise one incremental migration (`AddUserCreatedIndex`) ahead of a from-scratch baseline. A real MSSQL/PostgreSQL apply-and-verify run has not been done for any module's migration set.
- **Any developer database created against the old incremental MSSQL-only migration chain for `Location`/`Catalog`/`Orders`/`Inventory`/`Transfers`/`Purchasing` cannot be updated in place against the current baselines** — the migration ids differ, so `__EFMigrationsHistory` no longer matches. See [conventions/migrations.md § Resetting a developer database](conventions/migrations.md#resetting-a-developer-database).

## Dependency hygiene

- **Likely dead package references** (no source usage found): `Lightsoft.EventBus` (`Shared.csproj`), `Lightsoft.FileGenerator` (`Infrastructure.csproj`). Also a centrally-pinned `Microsoft.AspNetCore.Authentication.MicrosoftAccount` version with no project referencing it (the OIDC scheme uses `AddOpenIdConnect`, not `AddMicrosoftAccount`). Verify and remove if confirmed unused.
- **Undeclared transitive dependencies** — compile only because a `ProjectReference` happens to bring the package along:
  - `Infrastructure` uses `Mapster` and `Lightsoft.AspNetCore.Authorization`/`Lightsoft.Result` without declaring either (rides on `Shared`).
  - `Identity.Api` uses `Lightsoft.AspNetCore.Authorization`, `Lightsoft.Result`, `Lightsoft.Extensions`, `Lightsoft.Mediator` (via `GlobalUsings.cs`) without declaring any of them. (`Identity.Contracts` now declares `Lightsoft.Mediator`/`Lightsoft.Result` directly — only its use of `Lightsoft.AspNetCore.Authorization` is still transitive.)
  - `Identity.Api`'s `SearchUserQueryHandler` uses `Light.Specification` (`WhereIf`), provided by `Lightsoft.EntityFrameworkCore` declared by `Persistence.csproj`.
  - `StarterKit.WebApi` uses `Lightsoft.Serilog` without declaring it (only `Infrastructure.csproj` does).
  - Fragile: if an upstream project drops one of these packages, downstream projects break with no direct signal why. Recommend each project explicitly declare what it directly uses. `Organization`/`Approval`/`LeaveManagement`/`Location`/`Catalog`/`Currency`/`Orders`/`Inventory`/`Transfers`/`Purchasing` don't have this problem.
