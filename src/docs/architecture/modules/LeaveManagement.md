# Module Overview: LeaveManagement

## Purpose

Self-service CRUD for employee leave requests. The module owns only the leave-request record itself (`LeaveType`, date range, `Reason`, `Status`) — the actual multi-level approval workflow is delegated entirely to the generic `Approval` module via `IApprovalService`. `LeaveManagement` has no decide/approve endpoint of its own: an assigned approver acts on a leave request through `Approval`'s own self-service surface (`UserApprovalController`), and `LeaveManagement` learns the resulting status from an `ApprovalFinalizedIntegrationEvent` subscriber plus a periodic backstop sweep (see Notable Conventions). `LeaveRequest.ApprovalRequestId` is an opaque pointer back to the corresponding `Approval` request — no FK, the same cross-module-reference pattern already used by `Organization.Employee.UserId`, `Notifications.Notification.FromUserId`/`ToUserId`, and `Approval.ApprovalRequest.RequestType`/`RequestId`.

The workflow rules live on the `LeaveRequest` **aggregate**, not in the command handlers: the `Create` factory and the `LinkApprovalRequest`/`Resubmit`/`ReviseDetails`/`ApplyApprovalOutcome` behaviour methods enforce every invariant (date-range validity, who may still touch the request, the approval-id/status coupling on resubmit, never un-finalizing a status). A broken invariant throws a typed `Light.Exceptions.*`, following the same pattern `Approval.ApprovalRequest` established. Cross-row and cross-module orchestration that the aggregate itself cannot own — reconciling against Approval, the overlapping-period guard, resolving/validating an approver, building the `Approval` create payload — lives in `LeaveRequestApprovalCoordinator`, a shared application-layer seam the command handlers and the reconciliation sweep all call into instead of duplicating that choreography.

## Internal Layering

## Public Contract

### `LeaveRequestController` — self-service surface (route `leave_request`, **no class-level or action-level permission attribute at all**)

Authentication only, explicitly modeled on `Approval.Api/Controllers/UserApprovalController.cs`. A private `CanManage` (`currentUser.HasPermission(LeaveManagementPermissions.Requests.Manage)`) gates behavior *inside* each handler rather than via `[MustHavePermission(...)]` — every authenticated user can view/create/edit/delete their **own** leave requests regardless of permissions; `Manage` widens visibility/deletion but not editing (see Notable Conventions).

| Route | Verb | Request | Response |
|---|---|---|---|
| `api/v{version}/leave_request/search` | GET | Query `LeaveRequestSearchRequest` (`LeaveType?`, `Status?`, `EmployeeId?` — the last only honored when the caller has `leave.requests.manage`, otherwise every caller is hard-scoped to their own `UserId`) | `PagedResult<LeaveRequestDto>` — a pure read, no Approval call |
| `api/v{version}/leave_request/{id}` | GET | Route `id` | `Result<LeaveRequestDto>` — pure read; `NotFound` if missing, `Error` if the caller isn't the owning user and can't manage |
| `api/v{version}/leave_request/approvers` | GET | *(none)* | `Result<List<ApproverCandidateDto>>` — every eligible approver candidate for the caller's own department, via `IOrgDirectoryService.GetApproverCandidatesAsync`; `Error` if the caller has no linked employee record |
| `api/v{version}/leave_request` | POST | `CreateLeaveRequest { LeaveType, StartDate, EndDate, Reason?, ApproverEmployeeId }` | `Result<string>` (new id); builds a `DateRange`, checks for an overlapping period, resolves/validates the approver, then creates the single-level `Approval` request **first** and commits the local `LeaveRequest` row once it succeeds (see Notable Conventions — ordering, not a transaction) |
| `api/v{version}/leave_request/{id}` | PUT | `UpdateLeaveRequest { LeaveType, StartDate, EndDate, Reason?, ApproverEmployeeId? }` | `Result`; reconciles a stale local `Status` against Approval before the authorization gate; behavior then forks on `CanManage` — see Notable Conventions for the resubmission-vs-metadata-only split |
| `api/v{version}/leave_request/{id}` | DELETE | Route `id` | `Result`; reconciles a stale local `Status` against Approval before the status gate; non-manage callers may only delete their own `Pending`/`Rejected` requests; a still-`Pending` request's `Approval` request is cancelled first via `IApprovalService.CancelAsync` (passing the requester's own user id) and a failed cancel aborts a non-manage delete but only logs for a manage delete |

## Data Access

`LeaveManagementDbContext : BaseDbContext`, schema `"leave"`, registered via `Persistence.DbContextExtensions.AddConfiguredDbContext<LeaveManagementDbContext>(configuration, DbConnectionNames.LeaveManagement)`. `DbConnectionNames.LeaveManagement` aliases `DbConnectionNames.Default` ("DefaultConnection") — same physical database/connection string as every other module, separated only by schema (`leave`) + table name.

One table:

- **`LeaveRequests`** — two composite (non-unique) indexes: `(EmployeeId, Status)` (the `.manage`-scoped filter path) and `(UserId, Status)` (the self-service scope — ownership is keyed off `UserId`, see Notable Conventions). `UserId`/`EmployeeId`/`ApprovalRequestId` are `MaxLength(450)` string columns (`ApprovalRequestId` nullable, no FK — opaque reference into `Approval`); `Reason` is a nullable `MaxLength(1000)` column. `Period` (`DateRange`: `Start`, `End`) is mapped via `OwnsOne` — an EF owned type sharing the same table (table splitting) over the `StartDate`/`EndDate` columns, so it adds no schema. No FK constraints of any kind — `UserId`/`EmployeeId` are opaque references into `Identity`/`Organization`, same pattern as `Organization.Employee.UserId`.

Audited via `LeaveManagementDbContext.SaveChanges[Async]` → `AuditEntries(currentUser.UserId, clock.AuditTime, enableSoftDelete: false)` — the entity doesn't implement `ISoftDelete`, so this is no soft-delete support at all, not a comparable gap to `Identity`'s `User`.

`LeaveManagementContextInitialiser` applies migrations only (`MigrateDatabaseAsync`) — no `TrySeedAsync`/seed data; each provider's migrator `Program.cs` calls it. Migrations: see [../../conventions/migrations.md](../../conventions/migrations.md).

## Notable Conventions

- **The `LeaveRequest` aggregate owns every invariant; command handlers only orchestrate.** `private` constructor and `private set` properties; `Create` is the only way to build one (starts `Pending`, unlinked). `LinkApprovalRequest` attaches the freshly-created workflow (guarded: only once, only while `Pending` and unlinked). `Resubmit` is the owner-edit path — guarded by `IsOwnerActionable` (`Status is Pending or Rejected`) — and is the single place the approval-id swap and the `Status → Pending` reset are coupled. `ReviseDetails` is the `.manage`-only metadata correction: applies the edited fields on any status, never touches `Status`/`ApprovalRequestId`. `ApplyApprovalOutcome(approvalRequestId, outcome)` is the single reconcile choke point — it returns `false` (no-op) when the outcome belongs to a superseded workflow (an `approvalRequestId` mismatch, e.g. after a resubmit), when the request is already finalized (never un-finalize), or when the outcome equals the current status, and only every other case actually flips `Status`. Every reconcile call site (the two update/delete reconcile-before-authorize steps, the periodic sweep, and the integration-event handler) funnels through this one method.
- **`DateRange` is the module's one value object**, guarding the record's single true invariant (`End >= Start`) in exactly one place; `LeaveType`/`LeaveRequestStatus` stay plain enums since neither carries behavior. It inherits `Light.Domain.ValueObjects.ValueObject` (the same base `StarterKit.Shared.ActiveStatus` uses) rather than being a plain record — see the next bullet for why that matters beyond value equality — and mutates its own `Start`/`End` in place via an `internal Update(...)` method instead of ever being replaced by a new instance.
- **`Period` is mapped via `OwnsOne`, not `ComplexProperty`, and mutated in place, not reassigned — both for the same underlying EF reason.** `DateRange` sits over the `StartDate`/`EndDate` columns via EF's owned-type table splitting (same table). Two non-obvious gotchas drove the exact shape: (1) relational comparisons (`<=`, `>=`) on a complex-type member don't translate to SQL on this EF Core version — exactly what the overlap-check query needs — so the mapping uses `OwnsOne`. (2) Once `DateRange` is an owned type, reassigning `LeaveRequest.Period` to a *new* instance makes EF's change tracker emit the old instance as `Deleted` and the new one as `Added`; `Persistence`'s `TrackingExtensions.AuditEntries` resets any tracked `ValueObject` entry in `Deleted` back to `Unchanged` (a guard against nulling the owned columns on replacement) — but that reset then silently drops the *new* Start/End values instead of persisting them. `Resubmit`/`ReviseDetails` therefore mutate the existing tracked `DateRange` instance via `Period.Update(...)` instead, avoiding the replace-the-reference dance entirely — mirroring `ActiveStatus.Update(State)`'s own in-place-mutation convention for the same class of owned-type hazard.
- **An overlap-check business rule blocks double-booking.** `OverlappingLeaveRequestsSpec` matches same-employee rows whose status is `Pending` or `Approved` (the two "still occupies the calendar" statuses — `Rejected`/`Cancelled` never block) and whose stored period inclusively overlaps the candidate period; an optional `excludeRequestId` lets the row being edited/resubmitted skip itself. `LeaveRequestApprovalCoordinator.EnsureNoOverlapAsync` runs this check on create, on owner resubmission, and on a `.manage` metadata edit alike — enforced uniformly regardless of who is editing.
- **`LeaveRequestApprovalCoordinator` is the one shared seam for cross-row/cross-module orchestration**, called by all three command handlers and (via its `static` `TryApplyOutcome`) by the reconciliation sweep and the integration-event handler: `ReconcileStatusAsync` (pulls Approval's current status for a `ReconcilableLeaveRequestsSpec`-matching row by its stored `ApprovalRequestId`, through `IApprovalService.GetStatusAsync`, and applies it), `EnsureNoOverlapAsync`, `ResolveApproverAsync` (resolves + validates the chosen approver against `IOrgDirectoryService`'s candidate list), `CreateApprovalAsync` (builds the single-step `CreateApprovalRequest` payload — identical shape on create and resubmit — and calls `IApprovalService.CreateAsync`), plus the `static` `Guard`/`Guard<T>`/`ToResult`/`ToResult<T>` exception-translation helpers below. Cross-context ordering and compensation (the create-then-commit sequencing, the resubmit cancel-old-then-create-new sequencing, the best-effort compensating `CancelAsync` on a late failure) stay in the command handlers themselves, since that choreography is specific to each handler's failure-handling shape.
- **Domain guard failures are translated to `Result` the same way `ApprovalService` does at its own aggregate boundary.** `LeaveRequest`/`DateRange` throw typed `Light.Exceptions.*` (`ValidationException`/`ConflictException`) on a broken invariant. `LeaveRequestApprovalCoordinator.Guard`/`Guard<T>` run a domain-mutating call and catch `ExceptionBase`, returning a translated `Result`/`Result<T>` (`ConflictException → Conflict`, `ForbiddenException → Forbidden`, else `Error`); `ToResult`/`ToResult<T>` do the same translation for a call site whose own `try` must also drive a compensating action (the create/resubmit paths, where a domain throw after the `Approval` workflow already exists still needs the best-effort cancel). This keeps the cross-module-facing `Result` seam intact even though the aggregate itself signals failure by throwing.
- **Editing a `Pending`/`Rejected` request as its owner is a resubmission, not a plain update.** `Approval` has no "update" primitive — its `IApprovalService` seam is `CreateAsync`/`DecideAsync`/`CancelAsync` plus the read-only status lookups — so the owner-edit path in `UpdateLeaveRequestCommandHandler` cancels the prior approval request (only if it was still `Pending`, forwarding `entity.UserId` because `Approval` only lets the original requester cancel), re-resolves and re-validates the approver, and creates a brand-new approval request — the cancel and the create both run before `entity.Resubmit(...)` is called, so a failure on either side leaves the row untouched; only once the new `CreateAsync` succeeds does `Resubmit` apply the edited fields, swap `ApprovalRequestId`, and reset `Status` to `Pending`, followed by a single `SaveChangesAsync` wrapped in the same best-effort-cancel compensation the create handler uses. A `.manage`-scoped edit calls `ReviseDetails` instead — metadata-only, never resubmits to `Approval` — but still runs the overlap check.
- **Status is reconciled by an integration-event subscriber plus a periodic backstop — never on read.** `Approval` publishes `ApprovalFinalizedIntegrationEvent` when a workflow reaches `Approved`/`Rejected`; `ApprovalFinalizedIntegrationEventHandler` (in-process, runs in the deciding scope) looks the `LeaveRequest` up by id and applies the outcome via `LeaveRequestApprovalCoordinator.ApplyOutcomeAsync` — the whole body wrapped in try/catch-log so a reconcile failure never fails the originating decide. `LeaveRequestReconciliationService` (`BackgroundService`) is the delivery backstop: on a `PeriodicTimer` (`LeaveManagement:Reconciliation:IntervalMinutes`, default 5, validated `>= 1` on startup) it opens a fresh DI scope, loads up to `BatchSize` (default 200, validated `>= 1`) locally-`Pending` rows with a non-null `ApprovalRequestId` oldest-first via `ReconcilableLeaveRequestsSpec`, batches one `IApprovalService.GetStatusesAsync` call over the stored approval request ids (so a request forged against the same source record cannot shadow the real workflow), applies each via `LeaveRequestApprovalCoordinator.TryApplyOutcome` (the pure, non-saving half of `ApplyOutcomeAsync`), and — unlike the single-row reconcile call sites, which save immediately — writes back all changed rows in one batched `SaveChangesAsync` after the loop. The whole service is a no-op when `LeaveManagement:Reconciliation:Enabled` is `false`.
- **Update/Delete reconcile the local status against Approval before the authorization gate.** `UpdateLeaveRequestCommandHandler` and `DeleteLeaveRequestCommandHandler`, after loading the entity and before evaluating the ownership/status gate, call `coordinator.ReconcileStatusAsync` — so a caller cannot edit or delete a request whose workflow has already finalized just because the local copy is stale. This reconcile step commits on its own (a second, earlier `SaveChangesAsync`) before the rest of the command runs, deliberately — the corrected status is persisted even if the command then fails validation and returns an error.
- **Create is ordered, not transactional.** `CreateLeaveRequestCommandHandler` builds the `LeaveRequest` in memory (its `Id` is assigned at construction), calls `IApprovalService.CreateAsync` with that id as `RequestId`, and only on success does `entity.LinkApprovalRequest(...)` + a single `AddAsync` + `SaveChangesAsync`, all inside one try/catch. On approval-create failure nothing is persisted locally; if the linking guard or the local save then throws, a best-effort `CancelAsync` compensates and the caught exception is translated back to a `Result` (via `ToResult`/`ToResult<T>` when it was a domain guard, or a generic error message otherwise). There is no shared transaction across the two `DbContext`s — see `known-debt.md` P8 for the residual windows, including the equivalent one on the resubmit path.
- **Approver resolution always goes through `IOrgDirectoryService.GetApproverCandidatesAsync`, never a single top pick.** `LeaveRequestApprovalCoordinator.ResolveApproverAsync` resolves the *full* eligible-candidate list and validates the caller's chosen `ApproverEmployeeId` against it rather than trusting an arbitrary id or auto-picking one — see `modules/Organization.md § Notable Conventions` for the candidate-resolution algorithm itself.
- **`RequesterName` is sourced from `Organization`, not the JWT.** The create/update handlers call `IOrgDirectoryService.GetEmployeeNameAsync` to populate `CreateApprovalRequest.RequesterName`, because `JwtTokenIssuer.GetUserClaimsAsync` never stamps first/last-name claims. This differs from `Approval`'s own `UserApprovalController.PostAsync`, which keeps whatever `RequesterName` the client supplied verbatim. The label is still a denormalized snapshot with no backfill once written (`known-debt.md` D5).
- **Ownership is keyed off `UserId`, consistently.** Every self-service scoping check — the query handlers' visibility gate, the command handlers' edit/delete gate (`LeaveRequest.IsOwnedBy`) — compares against the caller's `UserId`. `EmployeeId` remains a stored field and a `.manage`-only search filter, but does not double as an ownership key anywhere.
- **Same opaque-cross-module-reference discipline as the rest of the solution.** `LeaveRequest.UserId`/`EmployeeId` point into `Identity`/`Organization` with no FK; `LeaveRequest.ApprovalRequestId` points into `Approval` with no FK. None of these are enforced at the database level.
- `LeaveManagement.Api.csproj` declares `<InternalsVisibleTo Include="LeaveManagement.Tests" />`. `tests/LeaveManagement.Tests` uses a Sqlite in-memory `LeaveManagementTestHost` so handler/coordinator/query tests exercise real EF Core behavior (including the `OwnsOne`-mapped `Period` in both predicates and projections), mocks `Organization.Contracts.Services.IOrgDirectoryService`/`Approval.Contracts.Services.IApprovalService` via Moq since both are real cross-module boundaries, and seeds arbitrary aggregate state for query-only tests via a reflection-based `LeaveRequestBuilder` test helper (mirroring `Approval.Tests`' `ApprovalEntityBuilder`).
