# Module Overview: LeaveManagement

## Purpose

Self-service CRUD for employee leave requests. The module owns only the leave-request record itself (`LeaveType`, date range, `Reason`, `Status`) — the actual multi-level approval workflow is delegated entirely to the generic `Approval` module via `IApprovalService`. `LeaveManagement` has no decide/approve endpoint of its own: an assigned approver acts on a leave request through `Approval`'s own self-service surface (`UserApprovalController`), and `LeaveManagement` reconciles the resulting status on read (see Notable Conventions). `LeaveRequest.ApprovalRequestId` is an opaque pointer back to the corresponding `Approval` request — no FK, the same cross-module-reference pattern already used by `Organization.Employee.UserId`, `Notifications.Notification.FromUserId`/`ToUserId`, and `Approval.ApprovalRequest.RequestType`/`RequestId`.

## Internal Layering

LeaveManagement is a **single-project module** (not split Domain/Application/Infrastructure/Api), following the same structural convention as `Identity`/`Notifications`/`Organization`/`Approval` — the template's 4-row project table doesn't apply as-is; adapted to the module's actual two projects:

## Public Contract

### `LeaveRequestController` — self-service surface (route `leave_request`, **no class-level or action-level permission attribute at all**)

Authentication only, explicitly modeled on `Approval.Api/Controllers/UserApprovalController.cs`. A private `CanManage` (`currentUser.HasPermission(LeaveManagementPermissions.Requests.Manage)`) gates behavior *inside* each handler rather than via `[MustHavePermission(...)]` — every authenticated user can view/create/edit/delete their **own** leave requests regardless of permissions; `Manage` widens visibility/deletion but not editing (see Notable Conventions).

| Route | Verb | Request | Response |
|---|---|---|---|
| `api/v{version}/leave_request/search` | GET | Query `LeaveRequestSearchRequest` (`LeaveType?`, `Status?`, `EmployeeId?` — the last only honored when the caller has `leave.requests.manage`, otherwise every caller is hard-scoped to their own `EmployeeId`) | `PagedResult<LeaveRequestDto>` |
| `api/v{version}/leave_request/{id}` | GET | Route `id` | `Result<LeaveRequestDto>` — `NotFound` if missing, `Error` if the caller isn't the owning employee and can't manage |
| `api/v{version}/leave_request/approvers` | GET | *(none)* | `Result<List<ApproverCandidateDto>>` — every eligible approver candidate for the caller's own department, via `IOrgDirectoryService.GetApproverCandidatesAsync`; `Error` if the caller has no linked employee record |
| `api/v{version}/leave_request` | POST | `CreateLeaveRequest { LeaveType, StartDate, EndDate, Reason?, ApproverEmployeeId }` | `Result<string>` (new id); validates `EndDate >= StartDate`, resolves candidates via `IOrgDirectoryService` and validates `ApproverEmployeeId` against that list, then creates the `LeaveRequest` row and a matching single-level `Approval` request via `IApprovalService.CreateAsync` — if the approval-side create fails, the just-inserted `LeaveRequest` row is deleted (best-effort compensation, not a transaction) |
| `api/v{version}/leave_request/{id}` | PUT | `UpdateLeaveRequest { LeaveType, StartDate, EndDate, Reason?, ApproverEmployeeId? }` | `Result`; behavior forks on `CanManage` — see Notable Conventions for the resubmission-vs-metadata-only split |
| `api/v{version}/leave_request/{id}` | DELETE | Route `id` | `Result`; non-manage callers may only delete their own `Pending`/`Rejected` requests; a still-`Pending` request's `Approval` request is cancelled first via `IApprovalService.CancelAsync` (passing the requester's own user id) |

## Data Access

`LeaveManagementDbContext : BaseDbContext`, schema `"leave"`, registered via `Persistence.DbContextExtensions.AddConfiguredDbContext<LeaveManagementDbContext>(configuration, DbConnectionNames.LeaveManagement)`. `DbConnectionNames.LeaveManagement` aliases `DbConnectionNames.Default` ("DefaultConnection") — same physical database/connection string as `Identity`/`Notifications`/`Organization`/`Approval`, separated only by schema (`leave`) + table name.

One table:

- **`LeaveRequests`** — composite (non-unique) index on `(EmployeeId, Status)`. `UserId`/`EmployeeId`/`ApprovalRequestId` are `MaxLength(450)` string columns (`ApprovalRequestId` nullable, no FK — opaque reference into `Approval`); `Reason` is a nullable `MaxLength(1000)` column. No FK constraints of any kind — `UserId`/`EmployeeId` are opaque references into `Identity`/`Organization`, same pattern as `Organization.Employee.UserId`.

Audited via `LeaveManagementDbContext.SaveChanges[Async]` → `AuditEntries(currentUser.UserId, clock.AuditTime, enableSoftDelete: false)` — the entity doesn't implement `ISoftDelete`, so this is no soft-delete support at all, not a comparable gap to `Identity`'s `User`.

Migrations exist for all three supported providers: `src/Migrations/{MSSQL,PostgreSQL,Sqlite}/LeaveManagement/` each hold **one baseline `CreateLeaveManagementSchema` migration** (dated 2026-09-07), following the same single-baseline convention `Organization`/`Approval` already established for this template repo's disposable dev databases. Each Migrations project's `.csproj` references `LeaveManagement.Api` and registers/invokes `LeaveManagementContextInitialiser` (`MigrateDatabaseAsync` only — no `TrySeedAsync`/seed data, matching `Approval`'s initialiser rather than `Organization`'s) alongside the other four module initialisers in each provider's `Program.cs`. The module starts empty until a user creates their first leave request.

## Notable Conventions

- **The permission model is deliberately minimal.** `LeaveManagementPermissions` defines **only one permission**, `leave.requests.manage`. Viewing/creating/editing/deleting your *own* leave requests needs no permission at all — every authenticated user can, gated purely by ownership (`entity.UserId == callerId`) plus status (`Pending`/`Rejected` are editable/deletable by their owner; any other status is final from the owner's point of view). `Manage` grants view-all (via `SearchLeaveRequestsQueryHandler`/`GetLeaveRequestByIdQueryHandler` skipping the ownership check) and delete-any, but **not** edit-any in the full sense: a `Manage`-scoped edit only mutates `LeaveType`/`StartDate`/`EndDate`/`Reason` and never touches `Status`/`ApprovalRequestId` — see the next bullet.
- **Editing a `Pending`/`Rejected` request as its owner is a resubmission, not a plain update.** `Approval` has no "update" primitive — its `IApprovalService` seam is `CreateAsync` / `DecideAsync` / `CancelAsync` plus the read-only `GetByRequestAsync` / `GetStatusByRequestAsync` / `GetStatusesByRequestAsync` lookups — so `UpdateLeaveRequestCommandHandler` cancels the prior approval request (`IApprovalService.CancelAsync`, only if it was still `Pending`, forwarding `entity.UserId` because `Approval` only lets the original requester cancel), re-resolves and re-validates the approver against a fresh `IOrgDirectoryService.GetApproverCandidatesAsync` call, and creates a brand-new approval request — resetting `Status` back to `Pending` and overwriting `ApprovalRequestId`. A `Manage`-scoped edit skips all of this entirely (metadata-only, as noted above) and never resubmits to `Approval`.
- **`LeaveManagement` still reconciles `Approval` status by polling on read, not by subscribing.** `Approval.Contracts` now defines `ApprovalFinalizedIntegrationEvent` (an `INotification` raised by `ApprovalService` after a request reaches a terminal state) that a module *could* handle in-process to reconcile status on push — but `LeaveManagement` deliberately does not subscribe to it yet, and `Approval`'s own `ApprovalStepPendingEvent`/`ApprovalFinalizedEvent` remain `internal` to `Approval.Api`. So the behavior is unchanged: `LeaveRequestStatusSync.ReconcileAsync` is called from both `GetLeaveRequestByIdQueryHandler` and `SearchLeaveRequestsQueryHandler`, and for every locally-`Pending` row with a non-null `ApprovalRequestId` it calls `IApprovalService.GetByRequestAsync("LeaveRequest", id)` and persists the resolved `Approved`/`Rejected`/`Cancelled` status if it has changed. Terminal statuses are never re-checked once reached. Revisit the polling approach if the module ever switches to handling `ApprovalFinalizedIntegrationEvent`.
- **Approver resolution always goes through `IOrgDirectoryService.GetApproverCandidatesAsync`, never a single top pick.** The endpoint/handlers resolve the *full* eligible-candidate list and validate the caller's chosen `ApproverEmployeeId` against it (`candidates.FirstOrDefault(x => x.EmployeeId == model.ApproverEmployeeId)`) rather than trusting an arbitrary id or auto-picking one — see `modules/Organization.md § Notable Conventions` for the candidate-resolution algorithm itself (manager-preference, hierarchy climb, exclude self/inactive/unlinked).
- **`RequesterName` is sourced from `Organization`, not the JWT.** `CreateLeaveRequestCommandHandler`/`UpdateLeaveRequestCommandHandler` call `IOrgDirectoryService.GetEmployeeNameAsync` to populate `CreateApprovalRequest.RequesterName`, because `JwtTokenIssuer.GetUserClaimsAsync` (`Identity.Api/Jwt/JwtTokenIssuer.cs`) never stamps first/last-name claims — it only merges `UserId`/`UserName`, role-derived permission claims, and per-user claims set via `IUserService.SetClaimAsync` (e.g. `employee_id`). This differs from `Approval`'s own `UserApprovalController.PostAsync`, which keeps whatever `RequesterName` the client supplied verbatim (see `modules/Approval.md`) — `LeaveManagement` instead resolves it server-side from a verifiable source. The label is still a denormalized snapshot with no backfill once written (`known-debt.md` D5).
- **Same opaque-cross-module-reference discipline as the rest of the solution.** `LeaveRequest.UserId`/`EmployeeId` point into `Identity`/`Organization` with no FK; `LeaveRequest.ApprovalRequestId` points into `Approval` with no FK. None of these are enforced at the database level — consistent with `Organization.Employee.UserId` and `Approval.ApprovalRequest.RequestType`/`RequestId`.
- `LeaveManagement.Api.csproj` declares `<InternalsVisibleTo Include="LeaveManagement.Tests" />`. `tests/LeaveManagement.Tests` uses a Sqlite in-memory `LeaveManagementTestHost` (mirroring `OrganizationTestHost`/`ApprovalTestHost`'s shape) so handler tests exercise real EF Core behavior, and mocks `Organization.Contracts.Services.IOrgDirectoryService`/`Approval.Contracts.Services.IApprovalService` via Moq, since both are real cross-module boundaries — the same rationale `Organization.Tests` uses for mocking `IUserService`. 30 test methods across the module's six command/query handlers.
