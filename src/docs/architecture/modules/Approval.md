# Module Overview: Approval

## Purpose

A generic, reusable multi-level approval-request engine — not tied to any specific request type. A consuming module (e.g. `LeaveManagement`) resolves the full approver chain itself (Approval has no knowledge of org structure, employee levels, or who should approve what) and calls `IApprovalService.CreateAsync` with an already-resolved `ApproverChain`. Approval then owns the generic mechanics: one `ApprovalRequest` aggregate per source record, a `Level`-ordered chain of `ApprovalStep`s, advancing `CurrentLevel` as each step is approved, finalizing the request as `Approved`/`Rejected`/`Cancelled`, and raising events so the relevant approver/requester gets notified and the owning module can reconcile status. `RequestType`/`RequestId` is an opaque pointer back to whatever record in the calling module triggered the approval (no FK — the same opaque-cross-module-reference pattern used by `Organization.Employee.UserId`, `Notifications.Notification.FromUserId`/`ToUserId`, and `LeaveManagement.LeaveRequest.ApprovalRequestId`).

The workflow rules live on the `ApprovalRequest` **aggregate**, not on a service: the `Create` factory enforces every chain invariant and returns a failed `IResult` rather than throwing, and `Decide`/`Cancel` guard state + single-approver authorization and queue domain events. `ApprovalService` is a thin coordinator around the aggregate — load, persist, drive the optimistic-concurrency retry, publish the cross-module integration event.

Because Approval cannot see identity or organization data, the calling side also passes the **display labels** it wants shown — `RequesterName` on the request, `ApproverName` on each `ApproverStepInput` — and the module stores them verbatim (see Notable Conventions, and `known-debt.md` D5 for the staleness trade-off). Optionally a request carries an admin-managed **document type** tag (`DocumentTypeId`) and a **deep link** (`DeepLinkUrl`) that the notification handlers use as the click target.

## Internal Layering

Approval is a **single-project module** (not split Domain/Application/Infrastructure/Api), following the same structural convention as `Identity`/`Notifications`/`Organization`/`LeaveManagement` — the template's 4-row project table doesn't apply as-is; adapted to the module's actual two projects:

| Project | Responsibility | Notes |
|---|---|---|
| `Approval.Contracts` | DTOs (`Approvals/ApprovalRequestDto` — includes `IList<ApprovalStepDto> Steps`, `RequesterName?`, `RequesterEmployeeId?`, `DocumentTypeId?`/`DocumentTypeName?`, `FinalizedAt?`; `Approvals/ApprovalStepDto` — includes `ApproverName?`; `DocumentTypes/ApprovalDocumentTypeDto`), a lean cross-module read-model (`Approvals/ApprovalStatusView(ApprovalRequestId, RequestType, RequestId, Status, CurrentLevel)`), the cross-module integration event (`Approvals/ApprovalFinalizedIntegrationEvent(RequestType, RequestId, ApprovalRequestId, Status) : INotification`), enums (`Approvals/ApprovalStatus`: `Pending`/`Approved`/`Rejected`/`Cancelled`; `Approvals/ApprovalStepStatus`: `Pending`/`Approved`/`Rejected`/`Skipped`; `Approvals/ApprovalRelation`: `All`/`Requested`/`AwaitingMyDecision`/`DecidedByMe`), input shapes (`Approvals/CreateApprovalRequest { RequestType, RequestId, RequesterUserId, RequesterEmployeeId?, RequesterName?, Title, Content?, DeepLinkUrl?, DocumentTypeId?, ApproverChain }`, `Approvals/ApproverStepInput(Level, ApproverUserId, ApproverEmployeeId, ApproverName?)`, `Approvals/DecideApprovalRequest(Approved, Comment?)`, `Approvals/ApprovalRequestSearchRequest : SearchQuery` with `RequestType?`/`Status?`, `Approvals/MyApprovalRequestSearchRequest : SearchQuery` with `Relation`/`RequestType?`/`Status?`, `DocumentTypes/CreateApprovalDocumentTypeRequest(Name, Code, Description?, IsActive)`), the module's cross-module seam (`Services/IApprovalService`: `CreateAsync`/`DecideAsync`/`CancelAsync`/`GetByRequestAsync`/`GetStatusByRequestAsync`/`GetStatusesByRequestAsync`), permission catalog (`Authorization/ApprovalPermissions` — `Group = "approval"`, `Requests.ViewAll` (**admin-only**; the self-service surface has no permission, just authentication), `DocumentTypes.{View,Create,Update,Delete}`; `Authorization/ApprovalPermissionProvider`). Declares `Lightsoft.AspNetCore.Authorization`, `Lightsoft.Mediator` (for `INotification`), and `Lightsoft.Result` directly; `GlobalUsings.cs` globals `Light.Contracts`/`Light.Mediator`/`StarterKit.Shared`. |
| `Approval.Api` | Single project organized by folder: `Domain/Approvals/` — the `ApprovalRequest` aggregate (private ctor; `Create` factory; `Decide`/`Cancel` methods; internal `RotateConcurrencyToken`; field-backed `Steps` collection) and its `ApprovalStep` child (private ctors; internal `Create`/`Approve`/`Reject`/`Skip`; `IsPending`), the anemic `ApprovalDocumentType` reference entity, `ApprovalRequestByIdSpec`, and the three domain events `ApprovalStepPendingEvent`/`ApprovalFinalizedEvent`/`ApprovalRequestCancelledEvent` (all `internal sealed record : DomainEvent`); all entities `: AuditableEntity`. `Data/` (`ApprovalDbContext`, `ApprovalContextInitialiser`). `Application/Approvals/{Commands,Queries,EventHandlers}` — `Commands`: `CreateApprovalRequestCommand`/`DecideApprovalStepCommand` (thin pass-throughs to `IApprovalService`); `Queries`: `GetApprovalRequestByIdQuery`/`SearchApprovalRequestsQuery` (admin), `GetMyApprovalRequestByIdQuery`/`SearchMyApprovalsQuery` (self-service, relation-scoped) — read `ApprovalDbContext` directly, no service indirection; `EventHandlers`: `ApprovalStepPendingEventHandler`/`ApprovalFinalizedEventHandler`/`ApprovalRequestCancelledEventHandler`, all `INotificationHandler<T>` each calling `Notifications.Contracts.Services.INotificationService.SendAsync` (see Dependencies). `Application/DocumentTypes/{Commands,Queries}` — full CRUD for the document-type catalog. `Services/ApprovalService.cs` (`internal`, implements `IApprovalService`). `Controllers/` (`ApprovalController`, `UserApprovalController`, `ApprovalDocumentTypeController`). `ApprovalModule.cs` (DI: DbContext + `IApprovalService` + permission provider). | `.Api` suffix follows the same convention as the other four modules (future-microservice-extraction candidate, not a fresh deviation). |

**`ApprovalService`/`IApprovalService` is the module's cross-module DI seam** — the same role `IUserService` plays for `Identity`, `INotificationService` for `Notifications`, and `IOrgDirectoryService` for `Organization`. Another module must be able to call it via constructor-injected DI, not `Mediator.Send` — the mediator commands/queries under `Application/` are `internal sealed record`s and not reachable cross-module. Since the DDD refactor the **business rules live on the `ApprovalRequest` aggregate**, not the service: `ApprovalService` loads the aggregate, calls `Create`/`Decide`/`Cancel`, persists, runs the optimistic-concurrency retry, and publishes `ApprovalFinalizedIntegrationEvent`. HTTP-only read-path logic and the document-type CRUD stay directly in their handlers (querying `ApprovalDbContext` via `Mapster.ProjectToType<T>`/`Adapt<T>` + `AsNoTracking`) — matching `Organization`'s inlined-handler convention for anything with no cross-module caller.

## Public Contract

### `ApprovalController` — admin surface (route `approval`, `[MustHavePermission(ApprovalPermissions.Requests.ViewAll)]` at class level)

| Route | Verb | Request | Response |
|---|---|---|---|
| `api/v{version}/approval` | GET | Query `ApprovalRequestSearchRequest` (`RequestType?`, `Status?`, plus `SearchQuery` paging / `SearchValue` matched against `Title`) | `PagedResult<ApprovalRequestDto>` — every request, unrestricted |
| `api/v{version}/approval/{id}` | GET | Route `id` | `Result<ApprovalRequestDto>` |
| `api/v{version}/approval` | POST | `CreateApprovalRequest` | `Result<string>` (new id) — ad-hoc/admin escape hatch; trusts the caller-supplied requester + chain as-is (see Notable Conventions) |

### `UserApprovalController` — self-service surface (route `approval/user`, authentication only, **no permission gate**)

Every query and command is scoped server-side to requests the current user is related to (as requester or as an approver on any step); "not found" and "not related" return the same `NotFound` so a user can't probe for requests they have no relation to.

| Route | Verb | Request | Response |
|---|---|---|---|
| `api/v{version}/approval/user` | GET | Query `MyApprovalRequestSearchRequest` (`Relation` = `All`/`Requested`/`AwaitingMyDecision`/`DecidedByMe`, `RequestType?`, `Status?`, paging) | `PagedResult<ApprovalRequestDto>` |
| `api/v{version}/approval/user/{id}` | GET | Route `id` | `Result<ApprovalRequestDto>` — 404 unless the caller is the requester or an approver on some step |
| `api/v{version}/approval/user/{id}/decide` | PUT | `DecideApprovalRequest { Approved, Comment? }` | `Result`; the caller must be the assigned approver for the current step (enforced in `ApprovalRequest.Decide`); approving advances `CurrentLevel` or finalizes as `Approved`, rejecting finalizes immediately as `Rejected` (a reason is required); a concurrent decision on the same request returns `Conflict` |
| `api/v{version}/approval/user` | POST | `CreateApprovalRequest` | `Result<string>` (new id) — `RequesterUserId` and `RequesterEmployeeId` are overridden server-side from the caller's identity + `employee_id` claim; `RequesterName` is kept as the client sent it (the JWT carries no name claim — same pattern as Notifications' caller-supplied `fromName`) |

### `ApprovalDocumentTypeController` — document-type catalog (route `approval/document_type`)

A small admin-managed reference list a request can optionally be tagged with. **The list read is available to any authenticated user** (it feeds the create-request document-type picker); the single-record read and every write are permission-gated.

| Route | Verb | Permission | Request | Response |
|---|---|---|---|---|
| `api/v{version}/approval/document_type` | GET | *(auth only)* | Query `activeOnly?` | `Result<IList<ApprovalDocumentTypeDto>>`, ordered by `Name` |
| `api/v{version}/approval/document_type/{id}` | GET | `approval.document_types.view` | Route `id` | `Result<ApprovalDocumentTypeDto>` |
| `api/v{version}/approval/document_type` | POST | `approval.document_types.create` | `CreateApprovalDocumentTypeRequest` | `Result<string>` (new id); rejects a duplicate `Code` |
| `api/v{version}/approval/document_type/{id}` | PUT | `approval.document_types.update` | `ApprovalDocumentTypeDto` (route/body id must match) | `Result` |
| `api/v{version}/approval/document_type/{id}` | DELETE | `approval.document_types.delete` | Route `id` | `Result`; blocked (pre-check **and** an FK-violation catch) if any `ApprovalRequest` still references the type |

### `IApprovalService` — cross-module seam (in-process only)

`CreateAsync` (validates the `DocumentTypeId` is a known active type, then builds + persists the aggregate), `DecideAsync`/`CancelAsync` (load aggregate → run the method → persist under the concurrency retry → publish `ApprovalFinalizedIntegrationEvent` once terminal), `GetByRequestAsync` (full `ApprovalRequestDto` for the most recent request tied to a source record), `GetStatusByRequestAsync` / `GetStatusesByRequestAsync` (lean single / batched `ApprovalStatusView` lookups for status reconciliation without pulling the steps).

## Data Access

`ApprovalDbContext : BaseDbContext`, schema `"approval"`, registered via `Persistence.DbContextExtensions.AddConfiguredDbContext<ApprovalDbContext>(configuration, DbConnectionNames.Approval)`. `DbConnectionNames.Approval` aliases `DbConnectionNames.Default` ("DefaultConnection") — same physical database/connection string as `Identity`/`Notifications`/`Organization`/`LeaveManagement`, separated only by schema (`approval`) + table name.

Three tables:

- **`ApprovalRequests`** — composite (non-unique) index on `(RequestType, RequestId, Created)` (the lookup key for `GetByRequestAsync`/`GetStatus*`, with the newest-first ordering baked in); indexes on `RequesterUserId` and `DocumentTypeId`. `ConcurrencyToken` is a required `MaxLength(32)` `IsConcurrencyToken()` column, **app-managed**: `ApprovalDbContext.RotateConcurrencyTokens()` rotates it (`Guid("N")`) on every modified `ApprovalRequest` during `SaveChanges[Async]`, so a decide/cancel racing another decision on the same request fails with `DbUpdateConcurrencyException` rather than silently clobbering it. `RequesterEmployeeId`/`RequesterName` are nullable `MaxLength` string columns (opaque bookkeeping / display label). `DocumentTypeId` is a nullable FK to `ApprovalDocumentTypes` with `DeleteBehavior.Restrict`.
- **`ApprovalSteps`** — index on `ApprovalRequestId` and on `ApproverUserId`; `ApproverName` is a nullable `MaxLength(256)` display-label column; FK to `ApprovalRequest` is `DeleteBehavior.Cascade`; the `ApprovalRequest.Steps` navigation is field-backed (`PropertyAccessMode.Field`) so the aggregate owns its collection.
- **`ApprovalDocumentTypes`** — unique index on `Code`; `Name`/`Code`/`Description` length-capped; `IsActive` defaults true. Left as a plain admin-managed lookup with public setters — deliberately not modelled as a rich aggregate.

All three are audited via `ApprovalDbContext.SaveChanges[Async]` → `AuditEntries(currentUser.UserId, clock.AuditTime, enableSoftDelete: false)` — no entity implements `ISoftDelete`, so this is no soft-delete support at all, not a comparable gap to `Identity`'s `User`. `SaveChangesAsync` additionally calls `IPublisher.DispatchDomainEvents(this)` after the commit to fan the aggregate's queued domain events out to their in-process `INotificationHandler`s; the synchronous `SaveChanges` override stays audit + token-rotation only because the write path (`ApprovalService`) is 100% async.

`GetByRequestAsync`/`GetStatusByRequestAsync` order `(RequestType, RequestId)` matches by `Created` desc and take the first rather than assuming uniqueness (a caller can legitimately re-raise a request for the same source record after a rejection — see `known-debt.md`); `GetStatusesByRequestAsync` does the same per id via an in-memory `GroupBy().First()` over the newest-first rows.

Migrations exist for all three supported providers: `src/Migrations/{MSSQL,PostgreSQL,Sqlite}/Approval/` each hold **one baseline `CreateApprovalSchema` migration** (dated 2026-09-06 — the incremental history was squashed per the disposable-dev-DB convention). That baseline predates the DDD refactor: the `ConcurrencyToken` column and the widened `(RequestType, RequestId, Created)` index are **not yet in it** and it needs regenerating before the schema change reaches a database. Each Migrations project's `.csproj` references `Approval.Api` and registers/invokes `ApprovalContextInitialiser` (`MigrateDatabaseAsync` only — no `TrySeedAsync`/seed data, matching `LeaveManagement`'s initialiser rather than `Organization`'s) alongside the other four module initialisers in each provider's `Program.cs`. The module starts genuinely empty until a consuming feature creates requests through `IApprovalService`.

## Notable Conventions

- **Business rules live on the `ApprovalRequest` aggregate, not `ApprovalService`.** `ApprovalRequest.Create` enforces the chain invariants — at least one level; positive, unique levels; every step carries an approver user id *and* employee id; a requester and a title are required — and returns a failed `IResult` rather than throwing. `Decide` guards `Status == Pending`, resolves the current step, checks the caller *is* that step's `ApproverUserId`, requires a reason on rejection, then either advances `CurrentLevel` to the next pending step (queuing `ApprovalStepPendingEvent`) or finalizes (queuing `ApprovalFinalizedEvent`). `Cancel` allows only the original requester and only while `Pending`. `ApprovalService` coordinates persistence and events around those calls; it holds no workflow logic itself. This follows the backend DDD-first convention (`src/CLAUDE.md § Design Approach`).
- **Approval never resolves approvers — or their display names — itself.** `CreateApprovalRequest.ApproverChain` must already be fully resolved by the calling module: level, approver user id, approver employee id, **and the display label** (`ApproverName`). Likewise `RequesterName` on the request. Approval has no knowledge of org structure, employee levels, or identity data, so it stores these verbatim. `UserApprovalController` keeps the client-supplied `RequesterName` because the JWT has no name claim; `LeaveManagement` instead resolves it server-side via `Organization` before calling `CreateAsync`. Trade-off: labels do not update if the underlying user/employee is renamed (`known-debt.md` D5).
- **`ApprovalStepStatus.Skipped` is set when a request finalizes.** `ApprovalRequest.SkipPendingSteps()` moves every still-`Pending` step to `Skipped` on rejection, final approval, or cancellation — so a request rejected at level 1 of 3 ends with step 1 `Rejected` and steps 2–3 `Skipped`.
- **Optimistic concurrency is app-managed, not provider-native.** The `ConcurrencyToken` string is rotated by `ApprovalDbContext` on every modified `ApprovalRequest`. `ApprovalService.DecideAsync`/`CancelAsync` wrap the save in a one-retry loop — on `DbUpdateConcurrencyException` they detach, reload the aggregate, and re-run the domain method once; a second failure returns `Result.Conflict` with a reload-and-retry message.
- **Two event channels, distinct audiences.** In-process **domain** events (`ApprovalStepPendingEvent`/`ApprovalFinalizedEvent`/`ApprovalRequestCancelledEvent`, `internal` to `Approval.Api`, dispatched post-commit by the DbContext) drive user-facing notifications inside the module. The `Contracts`-level `ApprovalFinalizedIntegrationEvent` (`: INotification`) is published directly by `ApprovalService` after a decide/cancel commits and reaches a terminal state, **best-effort** — a subscriber fault is caught and logged, never failing the decide/cancel call — for the owning module to reconcile its own status copy; a periodic backstop in that module is expected to cover a dropped delivery.
- **`ApprovalController`'s `POST approval` endpoint is an explicitly-documented escape hatch, not an oversight.** Real request types are expected to create their approval request via `IApprovalService` in-process instead. Unlike `UserApprovalController.PostAsync`, it trusts the caller's chosen requester/approver chain as-is.
- **The self-service surface (`UserApprovalController`) has no permission, only authentication** — mirroring `UserNotificationController`. Authorization is entirely relation-based (requester or approver on some step), enforced server-side in every query/command. `ApprovalPermissions.Requests` therefore only carries `ViewAll` (the admin surface); there is no `Requests.View`.
- **No delegate/backup-approver concept.** `ApprovalRequest.Decide` enforces single-approver-per-step authorization by comparing the current step's `ApproverUserId` to the caller — if the assigned approver is unavailable, nothing in this module lets anyone else act on their behalf.
- **`GET approval/document_type` (list) is intentionally ungated** so the create-request document-type picker can populate for any authenticated user; the by-id read and every write stay permission-gated. Same "a small reference list feeds a picker" reasoning as `GET employee/search` in `Organization`.
- Read-path handlers query `ApprovalDbContext` directly (`Mapster.ProjectToType<T>` for the `ProjectTo` queries, `.Adapt<T>()` after an `.Include` for `GetMyApprovalRequestByIdQueryHandler`, always `AsNoTracking`) — matching `Organization`'s "handlers own their logic directly" convention; write-path logic instead runs through the aggregate behind `IApprovalService` because it must be DI-reachable from other modules.
