# Module Overview: Approval

## Purpose

A generic, reusable multi-level approval-request engine — not tied to any specific request type. A consuming module (`LeaveManagement`, `Purchasing`) resolves the full approver chain itself (Approval has no knowledge of org structure, employee levels, or who should approve what) and calls `IApprovalService.CreateAsync` with an already-resolved `ApproverChain`. Approval then owns the generic mechanics: one `ApprovalRequest` aggregate per source record, a `Level`-ordered chain of `ApprovalStep`s, advancing `CurrentLevel` as each step is approved, finalizing the request as `Approved`/`Rejected`/`Cancelled`, and raising events so the relevant approver/requester gets notified and, on a terminal decision, the owning module can reconcile its own status copy. `RequestType`/`RequestId` is an opaque pointer back to whatever record in the calling module triggered the approval (no FK — the same opaque-cross-module-reference pattern used by `Organization.Employee.UserId`, `Notifications.Notification.FromUserId`/`ToUserId`, and `LeaveManagement.LeaveRequest.ApprovalRequestId`).

The workflow rules live on the `ApprovalRequest` **aggregate**, not on a service: the `Create` factory enforces every chain invariant, and `Decide`/`Cancel` guard state + single-approver authorization and queue domain events. A broken invariant throws a typed `Light.Exceptions.*`, so the `Domain/` layer carries no `Light.Contracts` dependency. `ApprovalService` is a thin coordinator around the aggregate — load, persist, drive the optimistic-concurrency retry, map any domain exception back to a `Result` for the `IApprovalService` seam, publish the cross-module integration event.

Because Approval cannot see identity or organization data, the calling side also passes the **display labels** it wants shown — `RequesterName` on the request, `ApproverName` on each `ApproverStepInput` — and the module stores them verbatim (see Notable Conventions, and `known-debt.md` D5 for the staleness trade-off). Optionally a request carries an admin-managed **document type** tag (`DocumentTypeId`) and a **deep link** (`DeepLinkUrl`) — the click target the notification handlers use for the **requester's** own notifications; an approver's notification instead always points at Approval's own decision page regardless of `DeepLinkUrl` (see Notable Conventions).

## Internal Layering

Approval is a **single-project module** (not split Domain/Application/Infrastructure/Api), following the same structural convention as `Identity`/`Notifications`/`Organization`/`LeaveManagement` — the template's 4-row project table doesn't apply as-is; adapted to the module's actual two projects:

| Project | Responsibility | Notes |
|---|---|---|
| `Approval.Contracts` | DTOs (`Approvals/ApprovalRequestDto` — includes `IList<ApprovalStepDto> Steps`, `RequesterName?`, `RequesterEmployeeId?`, `DocumentTypeId?`/`DocumentTypeName?`, `FinalizedAt?`; `Approvals/ApprovalStepDto` — includes `ApproverName?`; `DocumentTypes/ApprovalDocumentTypeDto`), a lean cross-module read-model (`Approvals/ApprovalStatusView(ApprovalRequestId, RequestType, RequestId, Status, CurrentLevel)`), the cross-module integration event (`Approvals/ApprovalFinalizedIntegrationEvent(RequestType, RequestId, ApprovalRequestId, Status) : INotification`), the reserved request-type registry (`Approvals/ApprovalRequestTypes` — `LeaveRequest`, `PurchaseOrder`, and `IsReserved`), enums (`Approvals/ApprovalStatus`: `Pending`/`Approved`/`Rejected`/`Cancelled`; `Approvals/ApprovalStepStatus`: `Pending`/`Approved`/`Rejected`/`Skipped`; `Approvals/ApprovalRelation`: `All`/`Requested`/`AwaitingMyDecision`/`DecidedByMe`), input shapes (`Approvals/CreateApprovalRequest { RequestType, RequestId, RequesterUserId, RequesterEmployeeId?, RequesterName?, Title, Content?, DeepLinkUrl?, DocumentTypeId?, ApproverChain }`, `Approvals/ApproverStepInput(Level, ApproverUserId, ApproverEmployeeId, ApproverName?)`, `Approvals/DecideApprovalRequest(Approved, Comment?)`, `Approvals/ApprovalRequestSearchRequest : SearchQuery` with `RequestType?`/`Status?`, `Approvals/MyApprovalRequestSearchRequest : SearchQuery` with `Relation`/`RequestType?`/`Status?`, `DocumentTypes/CreateApprovalDocumentTypeRequest(Name, Code, Description?, IsActive)`), the module's cross-module seam (`Services/IApprovalService`: `CreateAsync`/`DecideAsync`/`CancelAsync`/`GetStatusAsync`/`GetStatusesAsync`/`GetStatusByRequestAsync`/`GetStatusesByRequestAsync`), permission catalog (`Authorization/ApprovalPermissions` — `Group = "approval"`, `Requests.ViewAll` (**admin-only**; the self-service surface has no permission, just authentication), `DocumentTypes.{View,Create,Update,Delete}`; `Authorization/ApprovalPermissionProvider`). Declares `Lightsoft.AspNetCore.Authorization`, `Lightsoft.Mediator` (for `INotification`), and `Lightsoft.Result` directly; `GlobalUsings.cs` globals `Light.Contracts`/`Light.Mediator`/`StarterKit.Shared`. |
| `Approval.Api` | Single project organized by folder: `Domain/Approvals/` — the `ApprovalRequest` aggregate (private ctor; `Create` factory; `Decide`/`Cancel` methods; internal `RotateConcurrencyToken`; field-backed `_steps` collection exposed as a read-only copy via `Steps`) and its `ApprovalStep` child (private ctors; internal `Create`/`Approve`/`Reject`/`Skip`; `IsPending`), the anemic `ApprovalDocumentType` reference entity, `ApprovalRequestByIdSpec`, and the three domain events `ApprovalStepPendingEvent`/`ApprovalFinalizedEvent`/`ApprovalRequestCancelledEvent` (all `internal sealed record : DomainEvent`); all entities `: AuditableEntity`. `Data/` (`ApprovalDbContext`, `ApprovalContextInitialiser`). `Application/Approvals/{Commands,Queries,EventHandlers}` — `Commands`: `CreateApprovalRequestCommand` (with a validator rejecting reserved request types)/`DecideApprovalStepCommand` (thin pass-throughs to `IApprovalService`); `Queries`: `GetApprovalRequestByIdQuery`/`SearchApprovalRequestsQuery` (admin), `GetMyApprovalRequestByIdQuery`/`SearchMyApprovalsQuery` (self-service, relation-scoped) — read `ApprovalDbContext` directly, no service indirection; `EventHandlers`: `ApprovalStepPendingEventHandler`/`ApprovalFinalizedEventHandler`/`ApprovalRequestCancelledEventHandler`, all `INotificationHandler<T>` each calling `Notifications.Contracts.Services.INotificationService.SendAsync` (see Dependencies and Notable Conventions for how each picks its notification's `Url`). `Application/DocumentTypes/{Commands,Queries}` — full CRUD for the document-type catalog. `Services/ApprovalService.cs` (`internal`, implements `IApprovalService`). `Controllers/` (`ApprovalController`, `UserApprovalController`, `ApprovalDocumentTypeController`). `ApprovalModule.cs` (DI: DbContext + `IApprovalService` + permission provider). | `.Api` suffix follows the same convention as the other modules (future-microservice-extraction candidate, not a fresh deviation). |

**`ApprovalService`/`IApprovalService` is the module's cross-module DI seam** — the same role `IUserService` plays for `Identity`, `INotificationService` for `Notifications`, and `IOrgDirectoryService` for `Organization`. Another module must be able to call it via constructor-injected DI, not `Mediator.Send` — the mediator commands/queries under `Application/` are `internal sealed record`s and not reachable cross-module. The **business rules live on the `ApprovalRequest` aggregate**, not the service: `ApprovalService` loads the aggregate, calls `Create`/`Decide`/`Cancel`, persists, runs the optimistic-concurrency retry, maps any thrown domain exception back to a `Result`, and publishes `ApprovalFinalizedIntegrationEvent`. HTTP-only read-path logic and the document-type CRUD stay directly in their handlers (querying `ApprovalDbContext` via `Mapster.ProjectToType<T>`/`Adapt<T>` + `AsNoTracking`) — matching `Organization`'s inlined-handler convention for anything with no cross-module caller.

## Public Contract

### `ApprovalController` — admin surface (route `approval`, `[MustHavePermission(ApprovalPermissions.Requests.ViewAll)]` at class level)

| Route | Verb | Request | Response |
|---|---|---|---|
| `api/v{version}/approval` | GET | Query `ApprovalRequestSearchRequest` (`RequestType?`, `Status?`, plus `SearchQuery` paging / `SearchValue` matched against `Title`) | `PagedResult<ApprovalRequestDto>` — every request, unrestricted |
| `api/v{version}/approval/{id}` | GET | Route `id` | `Result<ApprovalRequestDto>` |
| `api/v{version}/approval` | POST | `CreateApprovalRequest` | `Result<string>` (new id) — ad-hoc/admin escape hatch; trusts the caller-supplied requester + chain as-is, but rejects a reserved request type (see Notable Conventions) |

### `UserApprovalController` — self-service surface (route `approval/user`, authentication only, **no permission gate**)

Every query and command is scoped server-side to requests the current user is related to (as requester or as an approver on any step); "not found" and "not related" return the same `NotFound` so a user can't probe for requests they have no relation to.

| Route | Verb | Request | Response |
|---|---|---|---|
| `api/v{version}/approval/user` | GET | Query `MyApprovalRequestSearchRequest` (`Relation` = `All`/`Requested`/`AwaitingMyDecision`/`DecidedByMe`, `RequestType?`, `Status?`, paging) | `PagedResult<ApprovalRequestDto>` |
| `api/v{version}/approval/user/{id}` | GET | Route `id` | `Result<ApprovalRequestDto>` — 404 unless the caller is the requester or an approver on some step |
| `api/v{version}/approval/user/{id}/decide` | PUT | `DecideApprovalRequest { Approved, Comment? }` | `Result`; the caller must be the assigned approver for the current step (enforced in `ApprovalRequest.Decide`); approving advances `CurrentLevel` or finalizes as `Approved`, rejecting finalizes immediately as `Rejected` (a reason is required); a concurrent decision on the same request returns `Conflict` |
| `api/v{version}/approval/user` | POST | `CreateApprovalRequest` | `Result<string>` (new id) — `RequesterUserId` and `RequesterEmployeeId` are overridden server-side from the caller's identity + `employee_id` claim; `RequesterName` is kept as the client sent it (the JWT carries no name claim — same pattern as Notifications' caller-supplied `fromName`); a reserved request type is rejected |

### `ApprovalDocumentTypeController` — document-type catalog (route `approval/document_type`)

A small admin-managed reference list a request can optionally be tagged with. **The list read is available to any authenticated user** (it feeds the create-request document-type picker); the single-record read and every write are permission-gated.

| Route | Verb | Permission | Request | Response |
|---|---|---|---|---|
| `api/v{version}/approval/document_type` | GET | *(auth only)* | Query `activeOnly?` | `Result<IList<ApprovalDocumentTypeDto>>`, ordered by `Name` |
| `api/v{version}/approval/document_type/{id}` | GET | `approval.document_types.view` | Route `id` | `Result<ApprovalDocumentTypeDto>` |
| `api/v{version}/approval/document_type` | POST | `approval.document_types.create` | `CreateApprovalDocumentTypeRequest` | `Result<string>` (new id); rejects a duplicate `Code` |
| `api/v{version}/approval/document_type/{id}` | PUT | `approval.document_types.update` | `ApprovalDocumentTypeDto` (route/body id must match) | `Result` |
| `api/v{version}/approval/document_type/{id}` | DELETE | `approval.document_types.delete` | Route `id` | `Result`; blocked (pre-check **and** an FK-violation catch) if any `ApprovalRequest` still references the type |

### `IApprovalService` — cross-module seam (in-process only)

`CreateAsync` (validates the `DocumentTypeId` is a known active type, then builds + persists the aggregate; it **accepts reserved request types** — that is how the owning module creates its own), `DecideAsync`/`CancelAsync` (load aggregate → run the method → persist under the concurrency retry → publish `ApprovalFinalizedIntegrationEvent` once terminal — see Notable Conventions for the cancel exception), and four lean `ApprovalStatusView` lookups for status reconciliation without pulling the steps:

- `GetStatusAsync(approvalRequestId)` / `GetStatusesAsync(approvalRequestIds)` — by the **exact stored approval request id**, the id the owning module keeps on its own record. This is what `LeaveManagement` and `Purchasing` reconcile with; another request that merely names the same source record cannot shadow it. Unknown ids are absent from the batched result.
- `GetStatusByRequestAsync(requestType, requestId)` / `GetStatusesByRequestAsync(requestType, requestIds)` — by source record; these return the **newest** request per `(RequestType, RequestId)`. No module calls them today.

There is no full-DTO `GetByRequestAsync`. Every method still returns `IResult`/`IResult<T>` (the lookups return the view or `null`) — a domain-invariant exception raised inside the aggregate is caught and mapped to a failed `Result` before it leaves the service (see Notable Conventions).

## Data Access

`ApprovalDbContext : BaseDbContext`, schema `"approval"`, registered via `Persistence.DbContextExtensions.AddConfiguredDbContext<ApprovalDbContext>(configuration, DbConnectionNames.Approval)`. `DbConnectionNames.Approval` aliases `DbConnectionNames.Default` ("DefaultConnection") — same physical database/connection string as every other module, separated only by schema (`approval`) + table name.

Three tables:

- **`ApprovalRequests`** — composite (non-unique) index on `(RequestType, RequestId, Created)` (the lookup key for `GetStatusByRequestAsync`/`GetStatusesByRequestAsync`, with the newest-first ordering baked in; the id lookups use the primary key); indexes on `RequesterUserId` and `DocumentTypeId`. `ConcurrencyToken` is a required `MaxLength(32)` `IsConcurrencyToken()` column, **app-managed**: `ApprovalDbContext.RotateConcurrencyTokens()` rotates it (`Guid("N")`) on every modified `ApprovalRequest` during `SaveChanges[Async]`, so a decide/cancel racing another decision on the same request fails with `DbUpdateConcurrencyException` rather than silently clobbering it. `RequesterEmployeeId`/`RequesterName` are nullable `MaxLength` string columns (opaque bookkeeping / display label). `DocumentTypeId` is a nullable FK to `ApprovalDocumentTypes` with `DeleteBehavior.Restrict`.
- **`ApprovalSteps`** — **unique** index on `(ApprovalRequestId, Level)` (one step per level per request — this is what lets `Decide` resolve the current step without a throw-on-duplicate guard) and an index on `ApproverUserId`; `ApproverName` is a nullable `MaxLength(256)` display-label column; FK to `ApprovalRequest` is `DeleteBehavior.Cascade`; the `ApprovalRequest.Steps` navigation is field-backed (`PropertyAccessMode.Field`) so the aggregate owns its collection.
- **`ApprovalDocumentTypes`** — unique index on `Code`; `Name`/`Code`/`Description` length-capped; `IsActive` defaults true. Left as a plain admin-managed lookup with public setters — deliberately not modelled as a rich aggregate.

All three are audited via `ApprovalDbContext.SaveChanges[Async]` → `AuditEntries(currentUser.UserId, clock.AuditTime, enableSoftDelete: false)` — no entity implements `ISoftDelete`, so this is no soft-delete support at all, not a comparable gap to `Identity`'s `User`. `SaveChangesAsync` additionally calls `IPublisher.DispatchDomainEvents(this)` after the commit — wrapped in a `try/catch` that logs a warning — to fan the aggregate's queued domain events out to their in-process `INotificationHandler`s, so a faulting handler cannot fail an already-committed decide/cancel. The synchronous `SaveChanges` override stays audit + token-rotation only because the write path (`ApprovalService`) is 100% async. This is the conforming reference for the repo-wide `DispatchDomainEvents` convention that `known-debt.md` P6 tracks as still-missing in `Identity`.

`GetStatusByRequestAsync`/`GetStatusesByRequestAsync` do not assume `(RequestType, RequestId)` is unique (a caller can legitimately re-raise a request for the same source record after a rejection, and `LeaveManagement`'s resubmit path does exactly that): the single lookup orders by `Created` desc and takes the first `ApprovalStatusView`; the batched one does the same per id via an in-memory `GroupBy().First()` over the newest-first rows.

`ApprovalContextInitialiser.InitialiseAsync()` applies migrations only — no `TrySeedAsync`/seed data; the module starts empty until a consuming feature creates requests through `IApprovalService`. Each provider's migrator `Program.cs` calls it. Migrations: see [../../conventions/migrations.md](../../conventions/migrations.md).

`LeaveManagement.Api` and `Purchasing.Api` reference `Approval.Contracts` and are the cross-module consumers, each in two ways:

- **`IApprovalService` (DI seam)** — they delegate the entire approval workflow: `CreateAsync` on create/submit/resubmission, `CancelAsync` on delete/withdraw/resubmission, and the by-id `GetStatusAsync` (single) / `GetStatusesAsync` (batched) lookups for status reconciliation. Their request types (`ApprovalRequestTypes.LeaveRequest` / `ApprovalRequestTypes.PurchaseOrder`) are reserved. Their read paths do not touch Approval at all.
- **`ApprovalFinalizedIntegrationEvent` subscriber** — each module's `ApprovalFinalizedIntegrationEventHandler` (`INotificationHandler<T>`, auto-registered) updates the local status when a workflow reaches `Approved`/`Rejected`, with the module's own reconciliation `BackgroundService` as the delivery backstop.

Client-side: `clients/admin/src/modules/approvals/` is the verified consumer of the module's HTTP surface (self-service + admin request lists, a request detail page with an inline decide action, and the document-type catalog).

## Notable Conventions

- **Business rules live on the `ApprovalRequest` aggregate, not `ApprovalService`.** `ApprovalRequest.Create` enforces the chain invariants — at least one level; positive, unique levels; every step carries an approver user id *and* employee id; a requester, a title, a non-blank request type, and a non-blank request id are required. `Decide` guards `Status == Pending`, resolves the current step (by `Level == CurrentLevel`, no throw-on-duplicate), checks that step is still `Pending`, checks the caller *is* that step's `ApproverUserId`, requires a reason on rejection, then either advances `CurrentLevel` to the next pending step (queuing `ApprovalStepPendingEvent`) or finalizes (queuing `ApprovalFinalizedEvent`). `Cancel` allows only the original requester and only while `Pending`. `ApprovalService` coordinates persistence and events around those calls; it holds no workflow logic itself. This follows the backend DDD-first convention (`src/CLAUDE.md § Design Approach`).
- **The aggregate signals invariant violations by throwing, not by returning `Result`.** `Create`/`Decide`/`Cancel` throw typed `Light.Exceptions.*` — `ValidationException` (shape / required-field rules), `ConflictException` (wrong state: already finalized, current step no longer pending), `ForbiddenException` (wrong caller: not the assigned approver, not the requester) — so the `Domain/` layer has no `Light.Contracts` dependency. `ApprovalService` is the translation boundary: it catches `Light.Exceptions.ExceptionBase` around each aggregate call and maps it to `Result.Error`/`Result.Conflict`/`Result.Forbidden`, keeping the cross-module `IApprovalService` seam `IResult`-based. Deliberate module-local deviation from the repo-wide "`Result` for expected failures" convention (`../../conventions/coding-conventions.md § Structural Conventions`). `LeaveManagement`'s own aggregate follows this exact same throw-then-translate shape (`LeaveRequestApprovalCoordinator.Guard`/`ToResult`).
- **Module-owned request types are reserved.** `ApprovalRequestTypes` lists the request types owned by another module (`LeaveRequest`, `PurchaseOrder`); `IsReserved` compares case-insensitively and ignores surrounding whitespace. A validator on `CreateApprovalRequestCommand` rejects a reserved type on **both** HTTP create endpoints (admin and self-service), so a caller cannot forge a request that shadows a genuine workflow or spoofs an approver's inbox. `IApprovalService.CreateAsync` itself does not check — the owning module creates its own reserved type in-process. A module that starts driving its own workflow through Approval must add its type to `ApprovalRequestTypes`.
- **Approval never resolves approvers — or their display names — itself.** `CreateApprovalRequest.ApproverChain` must already be fully resolved by the calling module: level, approver user id, approver employee id, **and the display label** (`ApproverName`). Likewise `RequesterName` on the request. Approval has no knowledge of org structure, employee levels, or identity data, so it stores these verbatim. `UserApprovalController` keeps the client-supplied `RequesterName` because the JWT has no name claim; `LeaveManagement` and `Purchasing` instead resolve it server-side via `Organization` before calling `CreateAsync`. Trade-off: labels do not update if the underlying user/employee is renamed (`known-debt.md` D5).
- **`ApprovalStepStatus.Skipped` is set when a request finalizes.** `ApprovalRequest.SkipPendingSteps()` moves every still-`Pending` step to `Skipped` on rejection, final approval, or cancellation — so a request rejected at level 1 of 3 ends with step 1 `Rejected` and steps 2–3 `Skipped`.
- **Optimistic concurrency is app-managed, not provider-native.** The `ConcurrencyToken` string is rotated by `ApprovalDbContext` on every modified `ApprovalRequest`. `ApprovalService.DecideAsync`/`CancelAsync` wrap the save in a one-retry loop — on `DbUpdateConcurrencyException` they detach, reload the aggregate, and re-run the domain method once; a second failure returns `Result.Conflict` with a reload-and-retry message.
- **A notification's `Url` depends on who the recipient is, not just `DeepLinkUrl`.** `ApprovalFinalizedEventHandler` notifies the **requester**, who owns the source module's record, so it uses `notification.DeepLinkUrl` verbatim (e.g. `LeaveManagement` points this at its own `/leave-requests/{id}` detail page). `ApprovalStepPendingEventHandler` and `ApprovalRequestCancelledEventHandler` instead notify an **approver**, who may not own — or even have access to — the requesting module's own record; both build `$"/approvals/requests/{notification.ApprovalRequestId}"`, Approval's own decision page that any assigned approver can always reach regardless of request type. Both events carry `ApprovalRequestId` for this.
- **Two event channels, distinct audiences.** In-process **domain** events (`ApprovalStepPendingEvent`/`ApprovalFinalizedEvent`/`ApprovalRequestCancelledEvent`, `internal` to `Approval.Api`, dispatched post-commit by the DbContext) drive user-facing notifications inside the module. The `Contracts`-level `ApprovalFinalizedIntegrationEvent` (`: INotification`) is published directly by `ApprovalService` after a **decide** commits to a terminal `Approved`/`Rejected` state, **best-effort** — a subscriber fault is caught and logged, never failing the decide call — for the owning module to reconcile its own status copy; each subscriber has a periodic reconciliation backstop for a dropped delivery. A requester-initiated **cancel does not publish** this event: the owning module always drives the cancel itself and learns the outcome directly from `CancelAsync`'s `IResult`, so re-publishing would only re-enter that same module's scope mid-command. A future non-requester cancel path (e.g. an admin force-cancel) must publish its own finalized event.
- **`ApprovalController`'s `POST approval` endpoint is an explicitly-documented escape hatch, not an oversight.** Real request types are expected to create their approval request via `IApprovalService` in-process instead. Unlike `UserApprovalController.PostAsync`, it trusts the caller's chosen requester/approver chain as-is; it still rejects reserved request types.
- **The self-service surface (`UserApprovalController`) has no permission, only authentication** — mirroring `UserNotificationController`. Authorization is entirely relation-based (requester or approver on some step), enforced server-side in every query/command. `ApprovalPermissions.Requests` therefore only carries `ViewAll` (the admin surface); there is no `Requests.View`.
- **No delegate/backup-approver concept.** `ApprovalRequest.Decide` enforces single-approver-per-step authorization by comparing the current step's `ApproverUserId` to the caller — if the assigned approver is unavailable, nothing in this module lets anyone else act on their behalf.
- **`GET approval/document_type` (list) is intentionally ungated** so the create-request document-type picker can populate for any authenticated user; the by-id read and every write stay permission-gated. Same "a small reference list feeds a picker" reasoning as `GET employee/search` in `Organization`.
- Read-path handlers query `ApprovalDbContext` directly (`Mapster.ProjectToType<T>` for the `ProjectTo` queries, `.Adapt<T>()` after an `.Include` for `GetMyApprovalRequestByIdQueryHandler`, always `AsNoTracking`) — matching `Organization`'s "handlers own their logic directly" convention; write-path logic instead runs through the aggregate behind `IApprovalService` because it must be DI-reachable from other modules.
